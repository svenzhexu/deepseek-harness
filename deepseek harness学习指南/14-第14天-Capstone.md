# 第 14 天 · Capstone

> **本日目标**：把前 13 天的零件拼成一个能演示、能交付、边界清晰的业务 agent。
> 今天的产出只有一个标准：**换一台机器，按你的 README 能跑起来。**

---

## 一、交付物定义

一个"业务助手"agent，至少包含六件事：

| # | 交付物 | 来自 |
|---|---|---|
| 1 | 一份组合定义（overlay 或 bundle） | 第 10 天 |
| 2 | 1–2 个业务工具 | 第 11 天 |
| 3 | 1 个业务 skill | 第 12 天 |
| 4 | 1 份 AGENTS.md（术语表 + 硬约束） | 第 12 天 |
| 5 | 1 条记忆路径（MCP 或自建） | 第 12 天 |
| 6 | 1 个外部调用入口（SDK 或 headless） | 第 13 天 |

可选的加分项：subagent 分工、定时任务、自定义设置项。

**不要贪多。** 六件事都做扎实，比十二件事半成品有价值。

---

## 二、组装顺序

按这个顺序做，每步都能验证，不会到最后才发现地基歪了：

### 步骤 1：先跑空壳

```powershell
pnpm dsh --profile web --patch ./tmp/my-agent.cordis.yml --dump-config
```

确认你的 overlay 被正确叠加。**这一步不做完，不要往下走。**

### 步骤 2：加工具，单独验证

只挂工具，在 UI 里手动让模型调用。确认：成功、业务失败、参数错误三种情况都对。

### 步骤 3：加指令与技能

先加 AGENTS.md（每轮可见），再加 skill（按需）。**分开加，分开验证**——一起加出问题，你不知道是谁的锅。

### 步骤 4：加记忆

先验证"能写进去"，再验证"新会话能读出来"。两步之间重启一次，确保不是内存幻觉。

### 步骤 5：接入外部调用

先 headless 跑通，再 SDK。headless 是最小路径，能排除掉一大类集成问题。

### 步骤 6：写 README

内容只有四段：

1. 这个 agent 解决什么问题。
2. 怎么装、怎么跑（含环境变量）。
3. 它的能力边界（能读什么、能写什么、什么要审批）。
4. 已知限制。

## 三、验收清单

全部打勾才算完成：

- [ ] 换一台机器，按 README 从零能跑起来
- [ ] agent 能在无人工干预下完成一条完整业务流
- [ ] 业务失败时返回结构化错误，不崩溃、不空转
- [ ] 参数写错时模型能自我修正并重试成功
- [ ] 关掉会话重开，记忆还在
- [ ] 越权操作被拒绝（不是"没被触发"，是**被明确拒绝**）
- [ ] `--dump-config` 里能找到你加的每一行
- [ ] 卸载 overlay 后，agent 恢复成原始形态（没有残留副作用）

最后一条最容易被忽略，但它验证的是**你有没有正确使用 `ctx.effect`**。

## 四、复盘：写下来才算学会

回答这五个问题，每个写 100 字：

1. **你放弃了哪些设计？为什么？**
   比如"没上向量库，因为工单量只有 2000 条，全文检索够用"。
2. **哪一处你一开始想改内核，后来发现配置就能解决？**
3. **你的 agent 最可能在什么情况下出错？** 现在有兜底吗？
4. **如果要把成本降一半，你会砍什么？**
5. **如果要让另一个同事接手，你的 README 缺什么？**

**放弃的理由比实现本身更能说明你真懂了。**

## 五、把它变成可分发的形态（可选）

如果这个 agent 要给团队用，把它从 overlay 升级成 bundle：

1. 建一个包，`package.json` 里加：

```json
"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
```

2. 把 overlay 的内容搬进 `cordis.patch.yml`。
3. **把每个裸插件名写进 `dependencies`**（否则解析不到，`verify-cordis-config` 会报）。
4. 用 `dsh plugin` 安装到目标 profile。

这样别人只需要一条命令就能用上，而不需要你发一份 YAML 让他手动改。

## 六、读完这本书之后

三条路，按投入排序：

**① 持续用**
把 agent 用起来。真实使用会暴露设计问题，比读代码有效十倍。

**② 参与贡献**
从小的开始：修一个文档错字、补一个测试、加一个工具。仓库的规矩都在根 `AGENTS.md` 里，读一遍再动手。

**③ 深挖某个方向**
选一条纵切面往下走：

| 方向 | 入口 |
|---|---|
| 循环与取消 | `packages/core/agent-loop` |
| 持久化与格式演进 | `packages/session`、`docs/cookbook/adding-a-session-format-version.md` |
| 沙箱与安全 | `packages/sandbox`、`docs/defensive-patterns/` |
| 客户端与 Remote | `packages/client`、`packages/api`、`docs/subsystems/web-client.md` |
| 多智能体 | `packages/subagent`、`packages/experimental/agent-team` |

**决策考古**是深挖时最有效的工具：`.agents/notes/implemented/` 里每个反直觉的设计都有记录。读代码卡住时，先 grep 这里。

## 七、最后一条建议

这套系统最好的学习方式不是读，是**改一个小东西然后观察它怎么失败**。

比如：

- 把一个 `next()` 删掉，看链为什么断。
- 把工具的 `isConcurrencySafe` 改成 `true` 但实际不安全，看会不会出错乱。
- 把压缩阈值调到很低，看历史怎么被遮蔽。

**每一次可控的破坏，都会让你对某条设计约束的理解从"知道"变成"信服"。**

## 八、全书回顾

用一张表收束：

| 天 | 一句话 |
|---|---|
| 1 | harness 是模型外面那层运行时，DSH 把它拆成了可替换的插件 |
| 2 | 注册即副作用，卸载即回滚；waterfall 忘了 `next()` 会静默短路 |
| 3 | 模型返回的是带类型的 chunk，不是字符串 |
| 4 | `followup` / `steer` / `inject` 的区别是"进哪个队列 + 要不要唤醒" |
| 5 | turn 可以没有 step；prompt 是历史，不是参数 |
| 6 | 日志是全集，历史是视图；压缩是遮蔽，不是删除 |
| 7 | 工具失败要返回结构化结果，不要抛 |
| 8 | prompt 是拼装出来的段落集合，上下文有缓存成本 |
| 9 | 记忆是四层机制的合称，DSH 故意不做向量库 |
| 10 | patch 是整行替换；组合先于代码 |
| 11 | 先设计呈现和失败，再写 `execute` |
| 12 | 每轮都要知道的进指令，按需的进 skill，能动手的做工具 |
| 13 | subagent 隔离上下文，workflow 编排扇出，goal 长跑同会话 |
| 14 | 换台机器能按 README 跑起来，才算做完了 |

如果这 14 句话你都能展开讲五分钟，这本书就读完了。
