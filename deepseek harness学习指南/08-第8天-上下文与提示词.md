# 第 8 天 · 上下文与提示词

> **本日目标**：回答一个问题——"模型每次请求，到底看到了什么？"答案不是一段字符串，而是三样东西的组合。

---

## 一、核心概念

### 8.1 请求由三部分组成

第 5 天提过一句结论，今天展开：

```
一次模型请求 = header.config          （路由、参数、缓存策略）
            + deriveMessages()        （历史，其中第一个节点是 system/message）
            + header.tools            （工具 schema）
```

**没有独立的 `system` 字段。** prompt 是历史里的一个节点。

这个设计带来三个能力，缺一不可：

- **可压缩**：prompt 和历史一起被 surface 操作处理。
- **可替换**：新 prompt 就是一条新的 `system/message` 节点。
- **可重放**：日志里有它，回放自然一致。

### 8.2 PromptSection：prompt 是一个拼装结果

system prompt 不是一段硬编码文本，而是一组**段落**（`PromptSection`）：

```ts
interface PromptSection {
  readonly name: string                                   // 唯一名，重名注册直接抛错
  readonly order: number                                  // 升序拼接
  readonly text: string | ((ctx: AssembleContext) => string)  // 静态或每次组装时求值
  readonly interpolate?: boolean                          // 是否插值 {{variable}}
  readonly complete?: boolean                             // 独占：只保留这一段
}
```

位置：`../docs/subsystems/system-prompt.md:48`

四条规则要记住：

1. **排序**：按 `order` 升序，相同 order 按名字的 code unit 顺序。
2. **`text` 可以是函数**：每次组装都会调用，可以读当前 `AssembleContext`（比如当前 agent、signal）。
3. **`complete` 是"独占"**：它仍然会跑完协作式组装（让工具、上下文、变量都解析出来），但最后只保留这一段。**两个 `complete` 同时生效 → 组装失败**。
4. **作用域**：`AssembleContext.scope` 决定哪些 provider 和监听器参与。

### 8.3 工具 schema 也来自 provider

```ts
interface ToolProviderResult {
  readonly schemas: readonly ToolSchema[]     // 本次组装可见的工具
  readonly knownNames?: readonly string[]     // 限制前的名字全集，用于区分"拼错"和"故意隐藏"
}
```

`knownNames` 的作用很实际：当配置里写了一个不存在的工具名，你想报"名字写错了"；但如果那个工具是被当前 scope 故意隐藏的，就**不该**报错，而应该说"它存在但在这个作用域不可见"。两种情况的诊断完全不同。

### 8.4 运行时上下文：另一种注入

除了 prompt 段落，还有一类内容叫**运行时上下文**（runtime context）：当前的 cwd、时间、workspace 信息等。

它和 prompt 段落的区别：

| | prompt 段落 | 运行时上下文 |
|---|---|---|
| 位置 | `system/message` 节点 | `user/message` 节点（source 为 `runtime-context`） |
| 更新方式 | 换一条 system 节点 | 每步重新投影，替换旧值 |
| 典型内容 | 人格、规则、技能目录 | 时间、目录、环境事实 |

**为什么放 user/message**：因为它是"当前事实"，会随时间变化；放进 system 会让缓存失效，放在 user 侧可以按需替换。

### 8.5 system/message 的三种落法

`renderPrompt()` 把组装结果渲染成文本，然后 agent-loop 决定怎么把它提交成节点（`docs/subsystems/system-prompt.md:44`）：

| 场景 | 做法 |
|---|---|
| 第一步 | 作为 surface 节点 0 追加 |
| 后续渲染文本变了 | **原地替换**那个节点 |
| 路由声明 `systemPromptUpdate: 'in-history'` 且是同一请求序列 | **追加到缓存历史之后** |

第三种是为 KV 缓存优化的：prompt 追加在历史尾部，前缀不变，缓存命中。这是"prompt 即历史"这个设计换来的实际收益。

### 8.6 上下文插件在哪

`packages/context/` 下每个包贡献一类上下文：

| 包 | 贡献什么 |
|---|---|
| `agent-instructions` | 仓库/工作区的 AGENTS.md 类指令 |
| `time-context` | 当前时间 |
| `file-reference` | 文件引用 |
| `session-reference` | 跨会话引用 |
| `harness-dev-context` | 开发态上下文 |

它们统一通过注册 prompt 段落或运行时上下文接入，**没有一个直接改请求**。这就是"扩展点优先于改循环"的具体表现。

## 三、精读片段

`../packages/core/agent-loop/src/agent.ts:416`：

```ts
const commits = this.systemPrompt.project(renderedPrompt, {
  inHistory: preparedCall?.systemPromptUpdate === 'in-history',
  startsSeries: startsRequestSeries
    || this.requestSurfaceGeneration !== this.session.surface.contentGeneration
    || (preparedCall?.toolUpdate === undefined && this.toolsChanged(assembly.tools)),
})
for (const { message, intent } of commits) {
  this.session.append('system/message', { turn, step, message }, intent)
}
```

这段代码回答了一个很容易忽略的问题：**prompt 变了，历史要不要跟着变？**

三个触发"新序列"的条件：

1. 这是新请求序列的第一条。
2. **surface 代际变了**（说明发生过 replace，比如压缩）——历史已经被改写，prompt 必须重新对齐。
3. 工具集变了，且当前路由不能增量更新工具。

第 2 条尤其微妙：压缩改了历史，prompt 就不能假设"我还挂在原来那个位置"。**任何改写历史的操作，都必须让 prompt 重新对齐**——这是"prompt 即历史"的代价。

## 四、动手

### 4.1 加一个 prompt 段落

写一个插件，注册一段 prompt：

```ts
export const inject = ['systemPrompt']

export function apply(ctx: Context) {
  ctx.systemPrompt.section({
    name: 'my-business-rules',
    order: 500,
    text: '处理工单时，必须先查客户等级，再判断 SLA。',
  })
}
```

重启，然后**去看会话日志**——你会发现它变成了一条 `system/message` 节点，而不是请求里的一个字段。

### 4.2 观察替换

改一下文本，重启，再做一次对话。在日志里找：新会话是追加，同一会话内是替换。

### 4.3 追 AGENTS.md

打开 `../packages/context/agent-instructions/README.md`，找到它扫描哪些文件名、按什么顺序合并。然后在仓库根改一下 `AGENTS.md` 里的一句话，观察下一次请求的 system 节点有没有变化。

## 五、验收

1. 一次请求由哪三部分组成？为什么没有 `system` 字段？
2. `PromptSection` 的四个字段各解决什么问题？两个 `complete` 会怎样？
3. prompt 段落的 `order` 相同会怎么排？为什么还要比名字？
4. 运行时上下文为什么放在 `user/message` 而不是 `system/message`？
5. 压缩之后，为什么 prompt 必须重新对齐？

## 六、常见误解

**"system prompt 就是一段固定的开头文本。"**
它是一组可以带作用域、可以每次求值、可以互相覆盖的段落。`complete` 段落甚至能让其他段落全部让位。

**"上下文越多越好。"**
上下文有成本：占窗口、稀释注意力、破坏缓存。每加一段都要问"模型真的需要每轮都看到它吗"——如果只在特定任务需要，做成 skill（第 12 天）。

**"改了 prompt 只有模型行为会变。"**
它还会改 KV 缓存命中率。放在历史尾部追加 vs 原地替换，缓存效果完全不同。
