# 第 6 天 · 会话日志与派生消息

> **本日目标**：读懂 `session.jsonl`，理解"日志是唯一真相"如何成立，以及 `deriveMessages()` 凭什么能保证模型看到的历史和记录的一致。

---

## 一、核心概念

### 6.1 事件溯源：只追加，不修改

一个会话就是一条 `SessionEvent[]`。它有三个硬约束：

1. **append-only**：没有 update，没有 delete。
2. **不可变**：每条事件在 append 时就被 `deepFreeze`。
3. **可校验**：每条事件在**落盘现场**验证，不合格直接抛错。

`append()` 的实现（`../packages/core/session/src/index.ts:798`）做了这些事：

```ts
const dataSnapshot = snapshotJsonValue(data)          // 快照，切断外部引用
if (dataSnapshot === undefined) throw ...             // 不可序列化 → 立即失败
const event = deepFreeze({ type, seq, time, data, ...surfaceMetadata })
validateSessionEventData(event, ...)                  // 现场校验
this.commit(event, entry)
```

**为什么在 append 现场校验**：注释说得很清楚——"日志是持久事实的来源，坏事件应该在写入点失败，而不是等到后端刷盘时才失败"。

### 6.2 事件目录

`SessionEventMap` 在 `../packages/core/session/src/types.ts:289` 起：

| 事件 | 位置 | 作用 |
|---|---|---|
| `turn/start` / `turn/end` | :289 / :298 | turn 边界，end 带 `reason` |
| `step/start` / `step/end` | :300 / :302 | step 边界 |
| `user/message` | :310 | 用户或注入的消息 |
| `system/message` | :331 | prompt 节点 |
| `assistant/message` | :342 | 成功的模型回复（内嵌流记录） |
| `assistant/attempt` | :356 | 失败的尝试（不进模型历史） |
| `tool/call` / `tool/result` | :362 / :376 | 工具调用与结果 |
| `request/header` / `request/context` | :391 / :403 | 请求路由与上下文快照 |
| `session/end-seed` | :428 | fork 时的继承切点 |

注意 `assistant/message` 和 `assistant/attempt` 的区分：**只有成功的消息进历史，失败的尝试只留证据**。这样重试不会污染上下文。

### 6.3 surface：只有五种事件进模型历史

日志里的事件很多，但**只有五种是"产消息"的**（`SurfaceEventType`，见 `types.ts:440`）：

```
system/message
developer/message
user/message
assistant/message
tool/result
```

其余事件（`turn/start`、`step/start`、`request/header`、`compaction/*`）只是记录，不进 surface。

注意 `tool/call` 不在里面——**工具的调用不是消息，工具的结果才是**。这也是为什么模型看到的工具结果，永远对应一条 `tool/result`。

`foldSurface()`（`../packages/core/session/src/surface.ts:594`）负责把这五种事件折叠成一条有序的"表面节点序列"。`deriveMessages()` 再按这个序列产出模型历史。

**这就是"日志"和"上下文"的分界**：日志是全量事实，surface 是其中的可见子集。

### 6.4 surfaceOp：遮蔽，而不是删除

surface 节点可以带一个 `surfaceOp`：

| 值 | 含义 |
|---|---|
| `append` | 正常追加 |
| `replace` | **替换一段区间**（压缩用） |

压缩做的事是：写一条 `compaction/summary` 记录摘要，再写一条带 `surfaceOp: { op: 'replace', startSeq, endSeq }` 的 `user/message`，**把那段历史从 surface 上遮蔽掉**。

原始事件一条没删。这是关键：**"忘记"是视图层的操作，不是存储层的操作。** 所以你可以审计、可以回滚、可以 fork 出另一个分支。

### 6.5 deriveMessages：带缓存的纯函数

`../packages/core/session/src/index.ts:984`：

```ts
deriveMessages(): Message[] {
  const surface = this.surface
  const nodes = surface.nodes
  const generation = surface.contentGeneration
  if (generation !== this.derivedGeneration) {   // 发生了 replace 或投影变化
    this.derived = []
    this.derivedNodes = 0
    this.derivedGeneration = generation
  }
  for (const seq of nodes.slice(this.derivedNodes)) {   // 只算新增的
    const msg = this.deriveEventMessage(this.log[seq]!)
    if (msg) this.derived.push(msg)
  }
  this.derivedNodes = nodes.length
  return [...this.derived]                         // 返回新数组
}
```

三个细节值得记：

1. **增量计算**：只处理 `derivedNodes` 之后的新节点，所以长会话不会每次全量重算。
2. **`contentGeneration` 失效**：一旦发生 `replace` 或消息投影变化，整个缓存重建——因为历史被改写了，增量失效。
3. **返回新数组，但消息对象共享且冻结**。注释写明："后来的 append 不会让调用者手里的数组变长；数组里的 `Message` 对象是共享且深度冻结的。"

### 6.6 持久化：代际与崩溃修复

日志落到磁盘是 JSONL，**按格式代际命名**（`session.vN.jsonl`）。几条必须知道的规则：

- 代际路径一旦提交，**永不重命名、覆盖、删除**。新版本写新文件。
- 恢复时选"数值最高的规范代际"。
- 读到更高版本 → 拒绝，不猜。
- 崩溃可能留下"半个 turn"。修复分两种：读路径**在内存里补齐**，写路径**追加合成的结束事件**。

**为什么这么重**：会话格式是产品对外的持久化契约，坏了就是用户数据坏了。

## 三、精读片段

`deriveMessages()` 里这一行看着不起眼：

```ts
for (const seq of nodes.slice(this.derivedNodes)) {
```

冒号后面那句注释是：

> Surface sequences are built from this.log — seq is always a valid index by construction.

意思是：**surface 节点存的是 seq，而 seq 就是日志数组的下标**。这是"日志不可变"换来的红利——因为从不删除，`seq` 可以当索引永久使用。如果允许删除或压缩掉数组，这个 O(1) 查找就不成立了。

**一个设计决定，会在很远的地方省下一行代码。** 找这种"看似随意其实有深意"的细节，是读源码最大的收获。

## 四、动手

### 4.1 逐行读一条真实日志

```powershell
# 位置见 docs/subsystems/persistence.md，通常是 $DSH_HOME 下的 sessions 目录
Get-ChildItem -Recurse -Filter "session*.jsonl*" $env:USERPROFILE\.dsh | Select-Object -First 5
```

打开一条，边读边标注：

1. 这个 turn 有几个 step？
2. `user/message` 出现在 `step/start` 之前还是之后？
3. `assistant/message` 里内嵌的 stream 记录长什么样？
4. 有没有 `request/header`？它记录了什么？

### 4.2 观察压缩前后

对一个长会话执行 `/compact`，然后：

- 对比压缩前后的 `deriveMessages()` 输出（可以写个小脚本，或者看 UI）。
- 在日志里找 `compaction/start` / `compaction/summary` / `compaction/end` 和那条带 `surfaceOp` 的 `user/message`。
- 确认：**原始事件还在。**

### 4.3 验证 fork

用 `Session.fork(source, boundary)` 从一个切点分叉，对比父子两条日志：子日志是不是带着 `session/end-seed`？继承的事件数量对不对？

## 六、常见误解

**"压缩就是删掉旧消息。"**
不是。压缩是**在表面层遮蔽**，原始日志一条不少。这个区别决定了你能不能审计、能不能 fork、能不能回滚。

**"`deriveMessages()` 每次调用都全量重算。"**
它有增量缓存。但发生 `replace` 时会整体重建——因为历史被改写了，增量不再有效。

**"日志格式可以随便改。"**
不可以。它是持久化契约，有版本号、有迁移链、有"已提交代际永不覆盖"的硬规矩。改它要走 `docs/cookbook/adding-a-session-format-version.md`。
