# 第 11 天 · 第一个业务工具

> **本日目标**：把"查工单"变成一个模型能调用、能失败、能在 UI 上正确展示的工具。
> 今天之后，你就有能力给这个 agent 加任何业务能力。

---

## 一、核心概念

### 11.1 先设计，再写代码

写工具前先回答四个问题，答案会直接决定代码形状：

| 问题 | 影响 |
|---|---|
| 模型需要哪些参数？能否更少？ | 参数越多，模型填错的概率越高 |
| 失败有几种？分别要告诉模型什么？ | 决定 `output.schema` 的设计 |
| 用户会怎么看到这个结果？ | 决定 `render` 与 `presentationMeta` |
| 它能和其他工具并行吗？ | 决定 `isConcurrencySafe` |

**第三问最容易跳过，但它决定了产品体验。** 仓库的规矩是"设计每个工具的 UI 呈现要先于实现"——因为呈现是契约的一部分，不是事后美化。

### 11.2 DefineToolOptions 的完整字段

`../packages/core/tools/src/schema.ts:483`：

| 字段 | 必填 | 作用 |
|---|---|---|
| `name` | 是 | 唯一名，进模型上下文 |
| `description` | 是 | 告诉模型什么时候该用 |
| `parameters` | 是 | 每属性的 schema，编译成对象根 |
| `output.schema` | 是 | 成功值的契约 |
| `output.render` | 是 | 把值变成 `ContentBlock[]` 给模型看 |
| `output.presentationMeta` | 否 | 给 UI 的纯函数元数据，可重放 |
| `execute` | 是 | 真正干活 |
| `isConcurrencySafe` | 否 | 能否并行 |
| `timeoutMs` | 否 | 协作式超时预算 |
| `deferLoading` | 否 | 延迟加载定义，省上下文 |
| `presentCall` / `presentResult` | 否 | 调用前/结果后的展示意图 |
| `projectContent` / `finalizeContent` | 否 | 结果内容的前后处理钩子 |

### 11.3 两种失败，两种处理

这是今天最重要的一条区分：

| 失败类型 | 例子 | 处理方式 |
|---|---|---|
| **参数非法** | 模型给了数字但 schema 要 string | 框架自动抛 `ToolArgsError`（`schema.ts:599`），你**不用管** |
| **业务失败** | 工单不存在、下游超时 | 你**返回**结构化结果，不要抛 |

为什么业务失败必须返回：模型需要看到"为什么失败"才能改策略（换 ID、换接口、告诉用户）。抛异常会把它压成一条无信息的错误串。

**实践做法**：在 `output.schema` 里预留状态字段，让成功和失败共用一套契约。比如：

```ts
{ ok: boolean, ticket?: {...}, error?: { code: string, message: string } }
```

### 11.4 ToolRunContext：execute 的第二个参数

`execute(args, exec)` 里的 `exec` 带：

- 执行身份（谁调的、哪个 agent）
- 取消信号（长任务必须检查）
- 嵌套/委派信息

**长任务一定要响应 `exec.signal`**。用户点了停止，工具还在跑，是体验灾难，也是资源泄漏。

### 11.5 注册即效果

```ts
export function apply(ctx: Context) {
  ctx.tools.register(lookupTicket)   // 返回值是 disposer
}
```

不用手动清理。但**如果你在 tool 里创建了长期资源**（连接池、定时器），要用 `ctx.effect()` 管住它们。

### 11.6 测试：单测不够

仓库规矩（`../packages/AGENTS.md`）：

> 产品可见插件需要**非单测的真实组合测试**。手工 `ctx.plugin(...)` 的套件不够。要通过 Loader 和应用/进程启动测试用 `cordis.yml`。

意思是：你的工具要在**真实的 boot 路径**下被验证一次，而不是只在内存里 `ctx.tools.register()` 后调一下。因为真实路径会暴露依赖解析、配置校验、加载顺序等问题。

## 三、精读片段

`../packages/core/tools/src/schema.ts:597`：

```ts
async execute(args: unknown, exec: ToolRunContext): Promise<JsonValue> {
  const violations = validate(args)
  if (violations.length > 0) throw new ToolArgsError(violations)
  return userExecute(args as InferArgs<S>, exec) as Promise<JsonValue>
},
```

三行代码，三个设计：

1. **参数校验在框架里做，不在你的 `execute` 里做。** 你拿到的 `args` 一定是合法的，可以放心断言类型。
2. **校验失败抛异常，业务失败不抛。** 边界划得很清楚：模型给错参数是"调用错误"，不是"业务结果"。
3. **返回类型是 `JsonValue`。** 工具的输出必须是可序列化的 JSON——因为它要进日志、要能重放。这解释了为什么 `output.schema` 是必需的。

## 四、动手

### 4.1 写工具

```ts
import { defineTool } from '@deepseek-ai/dsh-tools'

export const lookupTicket = defineTool({
  name: 'lookup_ticket',
  description: '按工单号查询工单详情。工单不存在时返回 ok:false。',
  parameters: {
    ticketId: {
      type: 'string',
      description: '工单号，形如 T-1024',
    },
  },
  output: {
    schema: {
      type: 'object',
      properties: {
        ok: { type: 'boolean' },
        title: { type: 'string' },
        status: { type: 'string' },
        error: {
          type: 'object',
          properties: { code: { type: 'string' }, message: { type: 'string' } },
        },
      },
    },
    render: (_args, value) => [
      { type: 'text', text: value.ok ? `${value.title}（${value.status}）` : value.error?.message ?? '查询失败' },
    ],
  },
  isConcurrencySafe: () => true,
  timeoutMs: 10_000,
  async execute({ ticketId }, exec) {
    const ticket = await db.find(ticketId, { signal: exec.signal })
    if (!ticket) {
      return { ok: false, error: { code: 'TICKET_NOT_FOUND', message: `工单 ${ticketId} 不存在` } }
    }
    return { ok: true, title: ticket.title, status: ticket.status }
  },
})
```

### 4.2 注册

```ts
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(lookupTicket)
}
```

### 4.3 挂进 profile 验证

写一个 overlay（第 10 天学过），把你自己的包挂上去，然后：

```powershell
pnpm dsh web --patch ./tmp/my-agent.cordis.yml
```

在 UI 里让模型调用它。**重点测试三种情况**：

1. 正常工单 → 返回结构化结果，UI 渲染正确。
2. 不存在的工单 → 模型收到 `ok:false`，能自己说"没找到"而不是崩。
3. 参数写错（比如传数字） → 框架抛 `ToolArgsError`，模型收到参数错误并重试。

### 4.4 补一个真实组合测试

用 Loader 启动一个最小 `cordis.yml`，断言工具被注册、能被调用。参考 `../docs/testing.md` 的测试策略。

## 六、常见误解

**"描述随便写，模型自己会看图。"**
描述是模型唯一的使用说明。写清楚"什么时候用、什么时候别用、参数什么格式"，比优化代码更重要。

**"工具越多越强大。"**
工具 schema 占上下文、分散注意力。同类工具能合并就合并；不常用的用 `deferLoading` 延迟加载。

**"`render` 是给用户看的，随便写。"**
它同时是模型看到的结果文本（`ContentBlock[]`）。写得太啰嗦会浪费上下文，写得太简略模型看不懂。
