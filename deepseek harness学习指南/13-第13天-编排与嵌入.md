## 一、核心概念

### 13.1 三种编排原语，解决三种不同问题

| 原语 | 解决什么 | 上下文 | 典型用法 |
|---|---|---|---|
| **subagent** | 上下文隔离 | 子 agent 有独立会话 | 调研、审查、并行探索 |
| **workflow** | 脚本化扇出 | 每个 agent 调用独立，编排在脚本里 | 批量处理、多角度分析 |
| **goal** | 长跑目标 | 同一个会话 | "把这个迁移做完" |

**选错的典型症状**：

- 用 subagent 做批量扇出 → 你得手动循环，还得自己管并发和结果汇总。
- 用 workflow 做需要连续上下文的任务 → 每轮都丢历史，模型反复重新理解。
- 用 goal 做一次性任务 → 引入不必要的轮次状态。

### 13.2 subagent：委派

`ctx.subagent` 是一个 provider 注册表。**挂服务本身不产生任何委派能力**，必须同时挂：

1. 服务：`dsh-subagent`
2. 一个 provider
3. 面向模型的工具：`dsh-tool-subagent`

最小配置（`../packages/subagent/subagent/README.md:36`）：

```yaml
- name: '@deepseek-ai/dsh-subagent'
- name: '@deepseek-ai/dsh-subagent-spawn-in-process'
- name: '@deepseek-ai/dsh-tool-subagent'
  config:
    provider: spawn
    toolName: subagent
```

**两类 provider，行为完全不同**：

| 类型 | provider | 语义 |
|---|---|---|
| 本地可续 | `spawn-in-process`、`fork-in-process` | 保留持久会话，之后还能继续对话 |
| 外部一次性 | `acp`、`dsh-sdk`、`codex`、`claude-code` | 执行一次，结束即终止 |

**spawn 和 fork 的区别**：

- `spawn`：全新会话，**不继承父对话**。你必须在任务描述里把必要上下文写全。
- `fork`：继承父会话**已完成的 turn**，子 agent 知道之前发生了什么。

选错的代价很直接：该 fork 的用了 spawn，子 agent 一脸茫然；该 spawn 的用了 fork，上下文被污染、成本翻倍。

**深度限制**：`maxDepth` 默认 `1`，只允许直接子级。要更深的委派树必须显式配置。

**结果投递**：工具立即返回子会话 id，父 agent 在子任务收敛时收到一条完成通知。所以你可以"派出去，先干别的"。

### 13.3 workflow：用脚本编排

workflow 执行一段 JavaScript 脚本，脚本里可以调用 agent。它的能力边界很明确：

- **有**：`agent()`、`parallel()`、`pipeline()`、`phase()`、`log()`、`args`
- **没有**：文件系统、网络、定时器、Node API

为什么故意拿掉这些：**编排逻辑应该是纯的**，副作用应该发生在 agent 里（它们有工具、有沙箱、有审计）。脚本只负责"谁在什么时候做什么"。

适合 workflow 的任务特征：

- 需要扇出到很多个独立单元（审 50 个文件、从 5 个角度研究）。
- 单元之间没有顺序依赖（用 `pipeline` 而不是先并行再汇总）。
- 结果要做结构化校验（schema 输出）。

### 13.4 goal：同一个会话里的长跑目标

goal 是**附加在一个已有会话上的持久目标**，有四个阶段：`active` / `paused` / `blocked` / `complete`，以及轮次上限。

和 subagent 的关键区别：

- goal **不新建会话**，它推动当前会话继续工作。
- goal 的每一轮是一次 goal 来源的 turn，但**人类插入的普通 turn 不消耗 goal 轮次**。
- goal 的激活状态是**进程本地**的，不写进持久日志——所以 resume 之后必须由人重新授权继续。

最后这条很重要：**自动继续不能被"重启"绕过**。这是安全设计，不是疏漏。

### 13.5 嵌入：四种方式

| 方式 | 形态 | 适合 |
|---|---|---|
| `dsh --profile headless "任务"` | 一次性 CLI 调用 | 脚本、定时任务、CI |
| TypeScript SDK | 进程中/子进程驱动 | Node 服务 |
| Python SDK | 子进程驱动 | Python 服务 |
| ACP | 标准协议 | 自动化客户端 |
| Web / HTTP | 浏览器 | 人工使用 |

TypeScript SDK 的最小用法（`../packages/sdk/client/README.md`）：

```ts
await using harness = new DeepSeekHarness({
  profile: 'sdk',
  patches: ['./automation.cordis.yml'],
})
const result = await harness.run('处理工单 T-1024')
console.log(result.finalResponse)
```

三个要点：

1. **profile 决定"跑的是什么 agent"**——这正是第 10 天学的组合能力在嵌入场景的体现。
2. **`patches` 让你在嵌入时也能定制**，不用改代码。
3. **`await using` 保证子进程被回收**。这是硬要求，不是风格偏好。

### 13.6 一次 `run()` 到底等什么

SDK 的 `run()` 不是"发一条消息就返回"，它：

1. 把 prompt 排进队列。
2. 等这条消息出现在**持久化的 inbox 收据**里。
3. 收集事件，直到整个 agent 回到 **idle**。
4. 返回 `finalResponse`（该区间内最后一条已提交的根会话 assistant 文本）。

**注意 `finalResponse` 不是"对这条 prompt 的因果回答"**——因为期间可能有 steer、注入、其他排队工作。如果你的业务要求严格的一问一答，要自己用 `requestId` 或消息 id 做关联。

## 三、精读片段

`../docs/subsystems/subagent.md:20`：

```ts
interface SubagentCapabilities {
  readonly agentOptions: boolean
  readonly agentPreset: boolean   // 支持独立于父级组合选择 preset
  readonly outputSchema: boolean
  readonly depthLimit: boolean
}
```

这个类型把"provider 能力差异"变成了**可查询的数据**，而不是"你试一下就知道行不行"。

流程是：请求进来 → 管理器检查每个被请求的选项 → **能力不支持就在启动前拒绝**。

**这是本仓库一条通用原则的实例**：*"Misconfiguration fails loud at load when self-contained, otherwise at the earliest resolvable point; never silently skip a missing referent."*（配置错误要在最早能确定的地方大声失败，绝不静默跳过。）

如果这里选择"忽略不支持的选项"，你会得到一个行为诡异但"能跑"的子 agent——比直接报错糟糕得多。

## 四、动手

### 4.1 挂一个 subagent

在 overlay 里加上最小三行配置，重启后让主 agent 做一件可以拆的事：

> "分别调研 packages/core 和 packages/llm 两个目录的职责，各写一段 100 字总结，然后合并。"

观察：

- 它有没有自动开子 agent？
- 子 agent 的会话在哪看？（会话列表里应该有子会话）
- 完成通知长什么样？

### 4.2 对照 spawn 与 fork

同样的任务，分别用 `spawn` 和 `fork` 的 provider 跑一次。重点观察：

- spawn 出来的子 agent 需不需要你在任务里重复背景？
- fork 出来的子 agent 是否知道刚才的对话？

### 4.3 用 SDK 调一次

写一个 15 行的脚本，用 TS SDK 起一次 `run()`，打印 `finalResponse` 和 `sessionId`。然后**用同一个 sessionId 再跑一次**，观察它是不是续上了之前的会话。

### 4.4 想清楚你的产品该用哪种

给你的业务画一张表：

| 场景 | 用哪个 | 为什么 |
|---|---|---|
| 用户点一次按钮，生成一份报告 | headless 或 SDK `run()` | 一次性 |
| 每天定时汇总 | schedule + headless | 无人值守 |
| 处理中需要查三个子系统 | subagent（并行） | 上下文隔离 |
| 一个跨天的大迁移 | goal | 同会话长跑 |

填不出这张表，说明你还没想清楚业务形态——那比选错 API 更严重。

## 六、常见误解

**"subagent 就是同一个 agent 换个会话。"**
不是。子 agent 有自己的工具集、自己的模型路由、自己的预算。它是**另一个 agent**，只是被父级委派。

**"workflow 是更高级的 subagent。"**
它们是并列的两种编排。workflow 的价值在"脚本可以写循环、分支、并发控制"，subagent 的价值在"一次委派"。

**"goal 会自动一直跑下去。"**
不会。它有轮次上限，而且激活状态在 resume 后是 disarmed 的——必须人工重新授权。这是防止失控的设计。
