# 第 7 天 · 工具管线

> **本日目标**：搞清楚一个工具从注册到执行的完整链路，以及为什么错误必须"返回"而不是"抛出"。

---

## 一、核心概念

### 7.1 工具的五个部分

一个 `ToolDefinition`（`../packages/core/tools/src/index.ts:224`）说的是五件事：

| 部分 | 作用 | 谁看 |
|---|---|---|
| `name` / `description` | 告诉模型这是什么 | 模型 |
| `parameters` | JSON Schema，约束参数 | 模型 |
| `execute` | 真正干活 | 运行时 |
| `isConcurrencySafe` | 能不能并行 | 调度器 |
| `presentation` | 结果怎么渲染 | UI |

**注意 `presentation` 是"永不进模型上下文"的**（`index.ts:271` 有明确注释）。它只影响用户看到什么，不影响模型思考什么。这个分界很重要：给工具加好看的 UI，不会烧 token。

### 7.2 defineTool：类型安全的注册方式

```ts
export function defineTool<const S, const O>(...)
```

位置：`../packages/core/tools/src/schema.ts:554`

它的价值是：**从 schema 推导出 `execute` 参数的类型**。你写：

```ts
defineTool({
  name: 'lookup_ticket',
  description: '按工单号查询工单详情',
  parameters: {
    ticketId: { type: 'string', description: '形如 T-1024' },
  },
  output: {
    schema: { type: 'object', properties: { title: { type: 'string' } } },
    render: (_args, value) => [{ type: 'text', text: value.title }],
  },
  async execute({ ticketId }) {
    // ticketId 自动推导为 string
  },
})
```

而不是手写一份 JSON Schema 再手写一遍 TS 类型，然后祈祷两者一致。

注意 `output` 是**必填**的（`DefineToolOptions.output`，`schema.ts:491`）：`schema` 约束成功值，`render` 把它变成模型可读的 `ContentBlock[]`。第 11 天会完整写一遍。

> 还有一条路径：直接给 `ctx.tools.register()` 传原始 JSON Schema。MCP 来的工具走的就是这条。`defineTool` 只是一等公民的便利层。

### 7.3 四个 waterfall 加一个广播

工具管线是 DSH 里扩展点最密集的地方：

| 事件 | 类型 | 用途 |
|---|---|---|
| `tools/pre-execute` | waterfall | **允许/拒绝**一次调用（权限、策略） |
| `tools/execute` | waterfall | **包裹整个派发生命周期**（超时、重试、指标） |
| `tools/post-execute` | waterfall | **改写结果** |
| `tools/result` | broadcast | 观察最终结果（只读） |
| `tools/change` | broadcast | 注册表变了 |

声明位置：`../packages/core/tools/src/index.ts:154-209`

**选哪个**，有明确规则：

- 要**否决** → `pre-execute`
- 要**控制执行边界**（比如加 deadline）→ `execute`
- 要**改结果** → `post-execute`
- 只想**知道** → `result`

还有一条：如果你需要"无论如何都不能被后续监听器推翻的拒绝"，用 `ctx.tools.guard()`，不要指望挂在 waterfall 里——**链上的顺序不保证**。

### 7.4 并行与独占

```ts
type ToolExecutionMode = { kind: 'parallel' } | { kind: 'exclusive' }
```

- `parallel`：可并发，最多 `maxParallelToolCalls` 个同时跑。
- `exclusive`：**独自运行并形成排序屏障**——它前面的要排空，它后面的要等它。

分类由 `isConcurrencySafe` 决定（`index.ts:1311`）：

```ts
executionMode(exec) {
  if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }   // 没声明 → 独占（保守）
  ...
}
```

**默认独占**是刻意的保守选择：不确定能不能并行，就串行。

还有一个细节：分类在**每次启动前重新读取**（`index.ts:1307` 附近注释），因为队列等待期间注册表可能变。这类"重读而不是缓存"的模式，在这个仓库里很常见——它防的是"决策和执行之间世界变了"。

### 7.5 错误必须返回，不能抛出

这是新手最容易错的一条。

模型的工具调用失败（文件不存在、API 超时、参数非法）是**正常业务**，不是异常。如果 `execute` 抛异常，上层只能把它变成一条通用的"工具执行失败"，模型拿不到有效信息，也就没法自我修正。

正确做法：返回结构化的失败结果。

```ts
return {
  ok: false,
  error: { code: 'TICKET_NOT_FOUND', message: `工单 ${ticketId} 不存在` },
}
```

**抛异常只用于"程序 bug"**：不变量被破坏、类型不该出现的情况。

### 7.6 工具结果是事件，不是返回值

工具跑完之后，结果会作为 `tool/result` **落进会话日志**（它是五种 surface 事件之一）。

这意味着：

- 模型下一轮看到的结果，是从日志派生的，不是内存里传过去的。
- 你可以在日志里看到每一次工具调用的完整输入输出。
- 重放、审计、fork 全都成立。

注意 `tool/call` 不是 surface 事件——**调用不是消息，结果才是**。

## 三、精读片段

`../packages/core/tools/src/index.ts:1311`：

```ts
executionMode(exec: ToolExecutionInput): ToolExecutionMode {
  if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }
  try {
    const concurrencySafe: unknown = tool.isConcurrencySafe(exec.arguments)
    return concurrencySafe === true ? { kind: 'parallel' } : { kind: 'exclusive' }
  } catch {
    return { kind: 'exclusive' }
  }
}
```

三行判断，三种保守：

1. 没声明 → 独占。
2. 声明了但返回值不是 `true`（比如返回了 `undefined` 或 truthy 的非布尔）→ 独占。
3. **分类函数自己抛错** → 独占。

第 3 条尤其值得学：**判断"能不能并行"的代码本身可能出错，这时应该退回最安全的假设**。这就是 fail-closed 的具体样子。

## 四、动手

### 4.1 写一个能失败的工具

```ts
const lookupTicket = defineTool({
  name: 'lookup_ticket',
  description: '按工单号查询工单详情。工单不存在时返回结构化错误。',
  parameters: {
    ticketId: { type: 'string', description: '工单号，形如 T-1024' },
  },
  output: {
    schema: { type: 'object', properties: { title: { type: 'string' }, status: { type: 'string' } } },
    render: (_args, value) => [{ type: 'text', text: `${value.title} / ${value.status}` }],
  },
  async execute({ ticketId }) {
    const ticket = await db.find(ticketId)
    if (!ticket) {
      // 业务失败：返回结构化结果，让模型能自我修正
      return { title: '', status: 'not-found' }
    }
    return { title: ticket.title, status: ticket.status }
  },
})
```

> 业务失败怎么表达，取决于你的 `output.schema` 设计。常见做法是在 schema 里留一个 `status` 或 `error` 字段，把成功和失败都纳入同一套契约——这样模型永远拿到可解析的结果，而不是一个异常字符串。

### 4.2 挂一个权限拦截器

```ts
ctx.on('tools/pre-execute', async (exec, next) => {
  if (exec.name === 'delete_ticket') {
    return { kind: 'deny', reason: '删除工单需要人工审批' }
  }
  return next()
})
```

**然后故意删掉 `return next()`**，观察所有其他工具是不是都失灵了。这个实验做一次，你永远不会再忘。

### 4.3 验证并行

写两个 `isConcurrencySafe: () => true` 的慢工具（各 sleep 1 秒），同时调用。观察总耗时是 1 秒还是 2 秒。再把其中一个改成 `false`，观察它变成屏障。

## 六、常见误解

**"工具越多越好。"**
工具 schema 会占上下文，也会稀释模型的注意力。能合并的合并，能延迟加载的用 `deferLoading`（见 `ToolSchema` 定义）。

**"`presentation` 只是美化。"**
它是"工具结果如何变成用户可读的界面"的契约。没有它，Web UI 里就是一段裸 JSON。写工具时应该和 `execute` 一起设计。

**"抛异常和返回失败差不多。"**
差很多。异常会丢失结构，模型无法据此修正；返回失败保留了 `code` 和上下文，模型可以换参数重试。
