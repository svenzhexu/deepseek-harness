# 第 9 天 · 记忆管理

> **本日目标**：把"记忆"这个词拆成四种真实机制，并说清 DSH 为什么**故意**不做向量库。

---

## 一、核心概念

### 9.1 四层记忆，四种机制

| 层次 | 存什么 | 载体 | 生命周期 |
|---|---|---|---|
| 工作记忆 | 本次请求的 prompt | `system/message` 节点 + 工具 schema | 一次请求 |
| 会话记忆 | 这次对话的全部事实 | `SessionEvent` 日志 + `deriveMessages()` | 一个 session |
| 压缩记忆 | 历史太长时的摘要 | `compaction/summary` + `surfaceOp: replace` | 一个 session |
| 长期记忆 | 跨会话的知识 | skills、AGENTS.md、session-query、外部 MCP | 永久 |

**"记忆"不是一个模块，是这四层的合称。** 任何关于"DSH 怎么做记忆"的问题，先问清楚问的是哪一层。

### 9.2 会话记忆：日志 + 派生

第 6 天已经讲过。要点复述：

- 日志是 append-only 的事实。
- `deriveMessages()` 从 surface 投影出模型历史。
- 两者不是同一份数据——**日志是全集，历史是视图**。

### 9.3 压缩记忆：遮蔽，不是删除

压缩是 DSH 里最精致的机制之一。

**三个事件构成一次压缩**（`../docs/subsystems/compaction.md:13`）：

| 事件 | 作用 |
|---|---|
| `compaction/start` | 获取**日志级锁**（`turn` 是数字则自动，`null` 则手动） |
| `compaction/summary` | 记录摘要、被遮蔽的 seq 集合、token 数、模型调用信封 |
| `compaction/end` | 释放锁，带 `error` 表示失败 |

**锁的意义**：`start` 先写，`end` 最后写。中途崩溃 → 留下一个"孤儿锁"（有 start 无 end），这是**可检测**的状态。如果反过来先写 end，崩溃就会伪装成"压缩成功"。

**摘要怎么进入历史**：不是作为新事件类型，而是复用 `user/message`，带：

```ts
surfaceOp: { op: 'replace', startSeq, endSeq }
```

**为什么复用 user/message**：因为它已经是 surface 事件，已经有替换语义，不需要新增一套机制。这是"用已有机制解决新问题"的典型。

**原始事件一条没删。** 审计、fork、回滚全部仍然可行。

### 9.4 投影：把日志折成状态

`session-projection` 是一个 seam：注册一个 `ProjectionDefinition`（`init` + `apply`），它就会把提交的事件增量折叠成一份 typed state。

消费方用 `stateOf()` 读。carrier 用 `snapshot()` 批量取客户端的裁剪视图。

一个真实例子在 agent-loop 里（`../packages/core/agent-loop/src/index.ts:57`）：

```ts
export const turnBoundaryProjectionDefinition = {
  key: 'turnBoundary',
  stateVersion: 2,
  stateSchema: turnBoundaryProjectionSchema,
  init: () => ({ openTurnStartSeq: null, lastStepStartSeq: null, lastStepBoundary: null, lastTurn: 0 }),
  apply: (state, event) => {
    switch (event.type) {
      case 'turn/start': return { ...state, openTurnStartSeq: event.seq, lastTurn: event.data.turn }
      case 'turn/end':   return { ...state, openTurnStartSeq: null }
      ...
    }
  },
}
```

**为什么投影重要**：它让"从日志算状态"变成 O(新增事件)，而不是每次 O(全量)。冷读、列表、客户端增量都靠它。

### 9.5 检索记忆：FTS，不是向量

`session-query` 提供跨会话的查询能力：

- 逻辑记录（`SessionRecord`）
- 精确事件读取
- 关系追踪（fork/子会话）
- **语义过滤器**
- **SQLite 全文检索**（`session-query-sqlite`）

**注意：这里的"语义"指的是按字段/标签过滤，不是 embedding 向量检索。**

实验性的 `session-search` 也是 FTS 索引，不是向量。

### 9.6 DSH 为什么不做向量记忆

这是一个设计取舍，值得想清楚：

| 维度 | 事件日志 | 向量库 |
|---|---|---|
| 可重放 | 完全可重放 | 不可重放（近似检索） |
| 可审计 | 每条事实可追溯 | 只能看到"命中了一段" |
| 一致性 | 一条日志一个真相 | 索引与原文可能漂移 |
| 语义召回 | 弱 | 强 |

DSH 选择了"可重放"作为地基，把"语义召回"交给外部。所以文档里给了三种 MCP memory 的接法（Memorix / MCP Reference Memory / Engram），**全部默认关闭**，并明确写着"只是互操作示例，不构成推荐"。

**练习**：想清楚如果你要做一个"跨 10 万条工单的语义检索"，应该放在哪一层——它显然不该进会话日志。

### 9.7 长期记忆的实际形态

DSH 内置的长期记忆其实是**文件**：

- `AGENTS.md` 类指令：常驻，每轮可见。
- skills：按需加载，有目录索引但正文不常驻。
- 工作区文件：模型用文件工具读写。

这三者共享一个性质：**人类可读、可版本控制、可 review**。这是刻意的——记忆如果只存在于向量里，你无法 code review 它。

## 三、精读片段

`../packages/compaction/compaction-basic/src/region.ts:117` 的 `selectCompactableRange()` 回答一个很实际的问题：**该压缩哪一段？**

朴素做法是"从头砍一半"。但真实系统里，有些内容不能动：

- 最近的若干轮（模型需要短期上下文）
- 工具调用的配对（`tool/call` 和 `tool/result` 必须一起留或一起删，否则历史非法）
- 系统提示节点

所以选择函数要返回一个**合法区间**，而不是一个长度。这类"边界条件决定实现"的代码，是业务代码里最值得借鉴的部分。

## 四、动手

### 4.1 观察压缩的完整生命周期

1. 让会话长到触发自动压缩，或手动执行 `/compact`。
2. 在日志里定位 `compaction/start` → `compaction/summary` → `compaction/end`。
3. 找那条带 `surfaceOp: {op:'replace'}` 的 `user/message`。
4. 确认被遮蔽的原始 seq 仍然在日志里。

### 4.2 写一个投影

注册一个统计"本会话用了多少次工具"的投影：

```ts
const toolCountProjection = {
  key: 'toolCount',
  stateVersion: 1,
  init: () => ({ count: 0 }),
  apply: (state, event) => event.type === 'tool/call' ? { count: state.count + 1 } : state,
}
```

挂上去，然后验证：新事件进来时它增量更新；卸载重挂时能从日志重算。

### 4.3 接一个外部记忆（可选）

按 `../docs/user/guide/mcp-memory.md` 接一个 MCP memory server，跑通"在这个会话里记住 → 开新会话想起来"。

**重点观察**：记忆工具是作为普通工具暴露给模型的（`mcp__<server>__<tool>`），它不改变任何内核机制。这是"能力靠插件，内核保持稳定"的又一个例子。

## 六、常见误解

**"压缩会删掉旧消息。"**
不会。旧事件永远在，只是从 surface 上被遮蔽。你可以 fork 出一个压缩前的分支。

**"`session-query` 是语义检索。"**
它是**结构化查询 + 全文检索**。真正的向量语义检索要靠外部 MCP 或自建。

**"长期记忆应该存数据库。"**
在 DSH 的取舍里，长期记忆优先做成**人类可读的文件**（AGENTS.md / skills），这样能 review、能进 git、能回滚。数据库适合放派生索引，不适合放唯一真相。
