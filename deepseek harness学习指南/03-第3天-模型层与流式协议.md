# 第 3 天 · 模型层与流式协议

> **本日目标**：搞清楚"一次模型调用"在 DSH 里到底是什么形状。今天之后，你看到任何模型相关代码都不会再觉得它是黑盒。

---

## 一、核心概念

### 3.1 模型返回的不是字符串

新手的心智模型是：`prompt → 文本`。

真实模型返回的是**一串带类型的事件**，因为它们必须同时承载四类信息：

| 信息 | 为什么不能塞进一个字符串 |
|---|---|
| 正文增量 | 要边生成边显示，靠字符流 |
| 思考过程 | 要和正文分开，不能进最终消息 |
| 工具调用 | 参数是**逐字拼出来的 JSON 片段**，必须能中途累加 |
| 用量与终止原因 | 决定这一步是继续、结束还是被截断 |

DSH 把这四类统一成了一个类型：`StreamChunk`。

### 3.2 ContentBlock：模型"说的话"的最小单位

```ts
interface ContentBlockMap {
  'text': TextBlock
  'reasoning': ReasoningBlock
  'image': ImageBlock
  'file': FileBlock
  'tool-call': ToolCallBlock
  'tool-addition': ToolAdditionBlock
  'tool-removal': ToolRemovalBlock
}
```

位置：`../packages/llm/llm/src/types.ts:137`

三个设计要点：

1. **它是 Map，不是 union 手写**。`ContentBlock` 由 Map 派生（`ContentBlockMap[keyof ContentBlockMap]`），插件可以通过声明合并往 Map 里加新块类型——**merge-extensible**。
2. **`tool-addition` / `tool-removal` 是内容块**。这意味着"给模型新增一个可用工具"本身是一条可以出现在对话里的消息，而不是只存在于请求头。
3. **switch 要兜底**。合并可扩展的联合类型不能 `assertNever`，必须落到默认分支。

### 3.3 StreamChunk：七个变体

```ts
type StreamChunk =
  | { type: 'block-start'; index: number; blockType: ContentBlockType }
  | { type: 'text-delta'; index: number; text: string }
  | { type: 'reasoning-delta'; index: number; text: string }
  | { type: 'tool-call-delta'; index: number; id: ToolCallId; name?: string; argumentsDelta: string }
  | { type: 'block-end'; index: number; block: ContentBlock }
  | { type: 'usage'; usage: TokenUsage }
  | { type: 'finish'; reason: FinishReason; replayState?: ReplayEnvelope }
```

位置：`../packages/llm/llm/src/types.ts:470`

**`index` 是关键**。模型可以交错地产生"文本块 0"和"工具调用块 1"，靠 index 把增量归到正确的块上。没有 index，流式装配不可能正确。

`block-end` 携带**装配完成的块**——注意是装配结果，不是原始片段。

### 3.4 FinishReason：五种结束方式

```ts
interface FinishReasonMap {
  'stop':        { kind: 'stop' }          // 正常结束
  'tool-calls':  { kind: 'tool-calls' }    // 要调工具，循环继续
  'max-tokens':  { kind: 'max-tokens' }    // 撞到输出上限
  'aborted':     { kind: 'aborted'; failure: LlmFailure }
  'error':       { kind: 'error'; failure: LlmFailure }
}
```

位置：`../packages/llm/llm/src/types.ts:156`

这里藏着 harness 的一个核心判断：**循环要不要继续，取决于 `FinishReason.kind`**，而不是"模型输出里有没有 tool_call 字样"。第 5 天你会看到 `step()` 怎么用它。

`max-tokens` 还有一个特殊语义：它是**粘性的**——一旦某个 step 撞了上限，后面正常完成的 step 不能把整个 turn 的结局"降级"回 completed。这条规则在 `agent.ts:338` 有一段注释专门说明。

### 3.5 TokenUsage 的计数是不重叠的

```ts
interface TokenUsage {
  inputTokens: number       // 仅未缓存的输入
  cacheReadTokens?: number
  cacheWriteTokens?: number
  ...
}
```

位置：`../packages/llm/llm/src/types.ts:175`

注释写得很直白：**计数互斥**，计费输入 = 三者之和。某些 provider 会把缓存命中折进 `prompt_tokens`，适配器必须减出来。

**为什么强调这个**：如果你要做成本核算或上下文预算，算错这里会导致严重偏差。这也是"模型层"看起来简单、实际很容易写错的原因。

### 3.6 适配器契约

`ctx.llm` 是一个 seam：Service Definition 在 `packages/llm/llm`，Provider 是 `llm-deepseek`、`llm-pi-ai` 等适配器。

一个适配器要实现两件事：

- `prepareCall(config, signal)` —— 解析并校验本次调用的路由（provider/model/参数），返回一个"准备好的调用能力"。
- `stream(request)` —— 发出请求，吐 `StreamChunk`。

**为什么拆成两步**：`prepareCall` 是**同步决策点**——它决定了这次调用的 header、prompt 更新模式（`systemPromptUpdate`）、工具更新能力。循环必须在真正发请求之前拿到这些信息，才能决定日志怎么写、消息怎么协调。第 5 天会展开。

## 三、精读片段

`BlockAssembler` 是整个流式处理的枢纽。它的职责可以概括成一句话：

> **吃进无序的 delta，吐出有序的块。**

伪代码如下（真实实现见 `assembler.ts`）：

```
on block-start(index, type)  → 建一个空的待装配块
on text-delta(index, text)   → 追加到该块的文本缓冲
on tool-call-delta(index,…)  → 追加 argumentsDelta 到该块的参数字符串
on block-end(index, block)   → 用权威块替换待装配块
on usage / finish            → 交给上层做结算
```

**为什么 `block-end` 还要带 `block`？** 因为增量可能不完整（比如 provider 在最后一个 delta 里补了字段）。以权威块为准，是对 provider 差异的兜底。

这段代码值得你亲手读一遍，它是"流式协议"这个抽象最具体的落地。

## 四、动手

### 4.1 走一遍仓库里已经记录好的流

不用真的调模型。仓库里有一批录制好的会话 fixture，里面包含完整的流式记录。

```powershell
# 找一份带 assistant/message 的 fixture
git grep -l "assistant/message" -- "*fixtures*"
```

打开任意一个，找到 `assistant/message` 事件，看它内嵌的 stream 记录数组——这就是一次真实的流。

### 4.2 手写一个最小适配器（不联网）

在 `tmp/` 下写一个只有一个 `stream()` 的假适配器，让它按顺序吐：

```
block-start(0, text)
text-delta(0, "你")
text-delta(0, "好")
block-end(0, {type:'text', text:'你好'})
usage({inputTokens: 10, outputTokens: 2})
finish('stop')
```

然后把它注册进一个测试上下文，观察 `BlockAssembler` 的输出。**跑通它，你就真正理解了协议。**

### 4.3 对照真实适配器

打开 `../packages/llm/llm-deepseek/src/`，找到它把 DeepSeek 的 SSE 响应翻译成 `StreamChunk` 的那段。重点看：

- 它怎么处理 `reasoning_content`（思考过程）？
- 它怎么把 `tool_calls` 的增量参数拼起来？
- 它怎么算 `TokenUsage`（尤其是缓存字段）？

## 六、常见误解

**"流式只是为了 UI 好看。"**
不是。流式是**能力**：工具参数必须边生成边拼（否则长参数要等整段返回），思考过程必须能和正文分开（否则会污染最终消息），断流时必须能保留已生成的部分（`aborted` 也要有 finish）。

**"适配器只要调通 HTTP 就行。"**
适配器真正的难点是**语义对齐**：缓存计数怎么折、工具参数怎么拼、思考内容放哪、终止原因怎么映射。这些都会直接影响模型行为和计费。

**"`ContentBlock` 是一个固定枚举。"**
它是 merge-extensible 的。这意味着你写 switch 时不能假设穷尽，必须处理未知类型——这也是为什么仓库规定"合并可扩展的联合类型不能用 `assertNever`"。
