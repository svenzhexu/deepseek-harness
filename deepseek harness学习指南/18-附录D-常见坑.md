# 附录 D · 常见坑

> 按"症状 → 原因 → 修法"组织。前五条是新手最常踩的，后五条是稍微深入之后才会遇到的。

---

## 坑 1：改完源码，客户端没变化

**症状**：改了 `packages/` 里的代码，重启桌面客户端，行为没变。

**原因**：客户端跑的是 `resources/app.asar` 里的**打包副本**，和你的源码目录没有任何关系。

**修法**：用 `pnpm dsh web` 从源码启动验证。要长期开发就跑 `pnpm run dev:web`。

---

## 坑 2：waterfall 忘了 `next()`

**症状**：你加了一个监听器，之后所有同类功能集体失灵，但没有任何报错。

**原因**：waterfall 的监听器必须显式 `return next()` 才把控制权交给下一个。不调用就是**静默短路整条链**。

**修法**：

```ts
ctx.on('tools/pre-execute', async (exec, next) => {
  if (shouldDeny(exec)) return { kind: 'deny', reason: '...' }
  return next()          // ← 这一行不能少
})
```

**判断**：看事件类型签名。有 `next: () => Promise<...>` 参数的就是 waterfall。

---

## 坑 3：patch 覆盖把别的配置抹了

**症状**：你只想改一个字段，结果同一条 config 里的其他字段全变成默认值了。

**原因**：patch 是**整行替换 config**，不是深合并。

**修法**：覆盖时写完整 config，或者确认其他字段用默认值没问题。

```yaml
# 错：以为只改 threshold
- id: compaction-basic
  config:
    threshold: 0.8

# 对：写全
- id: compaction-basic
  config:
    threshold: 0.8
    keepRecentTurns: 4
```

---

## 坑 4：插件加载了但 `ctx.xxx` 是 undefined

**症状**：插件跑起来了，但访问某个服务时报错。

**原因**：要么漏了 `inject` 声明，要么用 `ctx.xxx` 访问了一个可选服务。

**修法**：

- 必需依赖 → 写进 `inject`，框架会等它就绪。
- 可选依赖 → 用 `ctx.get('name')`，不要用属性访问。属性代理对拓扑敏感，`ctx.get` 读的是全局服务存储。

---

## 坑 5：改了内存里的消息数组

**症状**：当期会话看起来正常，但 resume / fork 之后历史错乱。

**原因**：违反了"模型可见 ⟺ 已记录"。模型历史必须由 `deriveMessages()` 从日志派生，不能手动拼一个数组塞进去。

**修法**：任何模型可见的新输入，都必须先成为 session 事件。要改已有消息内容，注册**纯消息投影**。

---

## 坑 6：把压缩当成"删除"

**症状**：以为压缩后原始数据没了，于是自己又存了一份备份。

**原因**：压缩是**surface 遮蔽**，原始事件一条不少。

**修法**：不需要备份。可以用 `sourceEventSeqs` 追溯被遮蔽的节点，也可以 fork 出压缩前的分支。

---

## 坑 7：在重试路径里重复落盘

**症状**：模型历史里出现重复的用户消息。

**原因**：重试在同一个 step 内循环，如果你在每次尝试都 `append('user/message')`，就会重复。

**修法**：用户消息只在**第一次尝试**落盘（参考 `agent.ts:426` 的 `if (firstAttempt)`）。重试复用已提交的输入。

---

## 坑 8：工具抛异常而不是返回失败

**症状**：业务失败时，模型看到一条没有信息的错误串，然后反复重试同一个错误调用。

**原因**：`execute` 抛异常会丢失结构，模型无法据此修正。

**修法**：业务失败返回符合 `output.schema` 的结构化结果；只有程序 bug 才抛。

---

## 坑 9：`inject` 依赖了具体 provider

**症状**：换一个 provider，你的插件就崩了。

**原因**：扩展插件应该依赖 Service Definition，绝不依赖具体实现。这是仓库的硬规则。

**修法**：`inject: ['shell']` 而不是 `inject: ['bashLocal']`。

---

## 坑 10：在 `apply` 外持有 ctx

**症状**：插件卸载后定时器还在跑，或者卸载时抛错。

**原因**：`apply` 结束后，`ctx` 属于那个 fiber。在外面用它注册的东西不受生命周期管理。

**修法**：所有注册都在 `apply` 内完成；需要跨异步边界使用的资源，用 `ctx.effect()` 管住。

---

## 附：三个排查动作

1. **`--dump-config`**：确认插件到底在不在、config 到底是什么。
2. **看会话日志**：确认事件有没有按预期落盘、顺序对不对。
3. **看测试**：`packages/*/*/tests/` 里通常有一个和你场景最接近的用例，照它写。

---

## 附：一个通用的定位口诀

> **先问"这是哪个域的问题"**：session（持久）、agent（实时）、tools（执行）、systemPrompt（组装）、llm（协议）。
>
> 域判断错了，你会在错误的文件里找一整天。
