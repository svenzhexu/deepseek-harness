服务：按名字使用能力

服务是 Cordis 解耦的核心。它把“我依赖某个类”换成“我需要一个叫 db 的能力”， 从而让提供者可以被替换、被隔离、被热更新，而消费者一行都不用改。这一章我们从写一个最小的服务开始。

难度 入门 阅读 约 30 分钟 前置 第 4–5 章 关键词 Service · inject · 声明合并
本章你将学会
  • 用 Service 基类提供一个具名能力；
  • 用声明合并让 ctx.greeter 获得类型；
  • 用 inject 让消费者等待提供者就绪；
  • 替换提供者、隔离服务实例，并理解为什么消费者不用改。

为什么是“名字”，而不是 import

传统写法里，消费者要使用数据库，就在文件顶部 import { Database } from './db.ts'。 这行 import 把消费者和某一个具体实现绑死了：换实现、换路径、换构造参数，都要改它。

Cordis 的做法是给能力起一个稳定的名字，比如 db。消费者只说“我要 db”， 至于 db 是文件、PostgreSQL 还是内存实现，由装配层决定。

维度直接 import服务寻址
依赖方向消费者 → 具体实现消费者 → 服务名 ← 提供者
替换实现改消费者代码换提供者即可
加载顺序调用方负责框架按依赖解析
测试mock 模块或依赖注入在子上下文里换提供者
多实例手动传参isolate 作用域
类比 · 点菜与厨房

消费者是在菜单上点“番茄炒蛋”，不是在厨房里指定“用三号锅、由张师傅做”。菜单上的名字（服务名）稳定， 后厨换人、换锅、换供应商（实现），顾客不需要知道。

第一个服务

写一个服务只需要三步：继承 Service、在构造函数里 super(ctx, '名字')、把它当插件挂载。

greeter.tsts
import { Context, Service } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    greeter: GreeterService
  }
}

export class GreeterService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'greeter')
  }

  greet(who: string) {
    return `Hello, ${who}!`
  }
}

const root = new Context()
await root.plugin(GreeterService)

console.log(root.greeter.greet('Cordis'))
终端output
Hello, Cordis!

这段代码里有两个层面同时发生，缺一不可：

  • 运行时：super(ctx, 'greeter') 把当前实例注册到 Reflect 服务仓库，名字是 greeter。 注册是一个 Effect，归当前 Fiber 所有，插件卸载时自动移除。
  • 编译时：declare module 块通过声明合并，把 greeter: GreeterService 加进 Context 接口。这样 ctx.greeter 才有类型；没有它，运行时仍然能跑，但编辑器会报错。
为什么用 ctx.plugin(GreeterService) 而不是 new

Service 的子类本身就是一个“类插件”。ctx.plugin 会为它创建 Fiber、检查依赖、校验配置， 再 new 出实例。直接 new GreeterService(root) 会绕过这层生命周期， 注册会记在根 Fiber 上，卸载插件时不会自动清理，也容易重复注册。

包名提醒：如果你使用的是上游包，declare module 的目标要改成 'cordis'； TypeScript 的声明合并按模块说明符精确匹配，写错包名不会报错，但 ctx.greeter 会失去类型。

消费者：声明依赖，而不是导入实现

消费者不 import GreeterService，只声明需要 greeter 这个服务：

consumer.tsts
import type { Context } from '@deepseek-ai/cordis'
import type {} from './greeter.ts'

export const name = 'consumer'
export const inject = ['greeter']

export function apply(ctx: Context) {
  console.log(ctx.greeter.greet('world'))
}

inject 让 Cordis 在服务就绪之前不执行 apply。因此进入函数体时， ctx.greeter 一定可用，不需要判空，也不需要 if (!db) return 之类的防御代码。

把两个文件放进同一个应用，顺序无关紧要：

main.tsts
import { Context } from '@deepseek-ai/cordis'
import { GreeterService } from './greeter.ts'
import { apply as consumer } from './consumer.ts'

const root = new Context()
await root.plugin(GreeterService)
await root.plugin({ inject: ['greeter'], apply: consumer })
注意 · 依赖是持续跟踪的

如果 GreeterService 被卸载，消费者也会被卸载；服务重新出现时，消费者会再次加载。 这就是“换实现不用改消费者”的底层机制：消费者不是一次性拿到引用，而是始终跟着服务走。

服务的三个角色

一个完整的能力接口（capability seam）由三个角色组成。理解这三个角色，比记住 API 更重要：

服务定义名字 + 方法语义 + 类型
←
提供者实现并注册到 ctx
→
消费者inject 后调用方法
角色负责不该负责
服务定义 服务名、公开方法、参数与返回类型、语义约定。 具体存储方式、网络细节、某个厂商的 SDK。
提供者 创建实例、注册服务、在卸载时释放资源。 假设消费者是谁、在什么时候调用。
消费者 声明依赖、调用方法、处理业务。 创建提供者、决定用哪个实现。

三者可以放在同一个包里，也可以分开。DeepSeek Harness 里常见的形式是：服务定义与默认提供者在同一个包， 消费者在另一个包；替换实现只需换一个提供者包。

替换提供者：消费者一行不改

下面这个例子先用内存实现，再用文件实现替换。消费者打印它当前拿到的实现，两次输出不同，代码却完全相同。

swap.tsts
import { Context, Service } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    db: { query(): string }
  }
}

class MemoryDb extends Service {
  constructor(ctx: Context) {
    super(ctx, 'db')
  }
  query() {
    return 'memory'
  }
}

class FileDb extends Service {
  constructor(ctx: Context) {
    super(ctx, 'db')
  }
  query() {
    return 'file'
  }
}

const root = new Context()
let provider = await root.plugin(MemoryDb)

const consumer = await root.plugin(Object.assign((ctx: Context) => {
  console.log('using', ctx.db.query())
}, { inject: ['db'] }))

await provider.dispose()
provider = await root.plugin(FileDb)
await consumer
终端output
using memory
using file

注意这里发生的三件事：

  1. provider.dispose() 移除了 db 服务；
  2. Cordis 发现消费者依赖 db，把它卸载，清理它注册的东西；
  3. FileDb 注册后，消费者被重新加载，再次执行 apply。

消费者没有重新 import，也没有重新创建，它只是“重新加载”了。这正是声明式依赖的价值： 消费者描述“我需要什么”，而不描述“我从哪里拿”。

多实例：同一服务名，不同实现

有一种常见误解：服务名是全局的，所以一个应用只能有一个 db。其实不是。 通过 isolate，你可以在同一棵插件树里创建多个互不干扰的作用域：

tenants.tsts
import { Context } from '@deepseek-ai/cordis'

const root = new Context()

const tenantA = root.isolate('db')
const tenantB = root.isolate('db')

await tenantA.plugin(MemoryDb)
await tenantB.plugin(FileDb)

tenantA.plugin(Object.assign((ctx: Context) => {
  console.log('tenant A:', ctx.db.query())
}, { inject: ['db'] }))

tenantB.plugin(Object.assign((ctx: Context) => {
  console.log('tenant B:', ctx.db.query())
}, { inject: ['db'] }))
终端output
tenant A: memory
tenant B: file

这正是多租户、测试替身、按环境切换实现的基础。Loader 的 isolate 配置只是把这个 API 搬到了 YAML 里，见第 9 章。

可选依赖与降级

不是所有依赖都是硬性的。比如“有通知服务就发通知，没有就只写日志”。这种情况下不要写 inject，用 ctx.get：

optional.tsts
export function apply(ctx: Context) {
  const notifier = ctx.get('notifier')
  if (notifier) {
    notifier.send('hello')
  } else {
    console.log('no notifier, fallback to log')
  }
}
不要把可选依赖缓存起来

ctx.get 拿到的值可能随时因为提供者卸载而失效。不要把它存到模块级变量里、也不要在一次操作之外复用。 每次用到时重新获取，或者干脆声明为硬依赖，让 Cordis 帮你管理生命周期。

Service 的进阶能力

下面这些先了解“存在”，需要时再回来看：

能力写法用途
异步初始化 [Service.init]() 构造函数之后运行，可异步；常用于建立连接。抛出则插件 FAILED。
可用性判断 [Service.check]() 返回 false 时，依赖它的插件继续保持 PENDING。
可调用服务 [Service.invoke](...) 让 ctx.logger(...) 这种“服务也是函数”的写法成立。
配置拦截 [Service.config] 声明服务接受的 intercept 配置类型。
实例派生 [Service.extend](props) 基于当前服务创建带额外属性的视图，框架内部使用。

其中“异步初始化”最实用。如果你的服务需要连接数据库、拉取远程配置，不要把这些工作塞进构造函数， 而是放到 [Service.init]：

async-service.tsts
import { Context, Service } from '@deepseek-ai/cordis'

// 省略 Connection 接口与 connect() 的实现
class Database extends Service {
  private connection?: Connection

  constructor(ctx: Context) {
    super(ctx, 'db')
  }

  async [Service.init]() {
    this.connection = await connect()
    return () => this.connection?.close()
  }

  query(sql: string) {
    return this.connection!.query(sql)
  }
}

返回的函数会被当作这个服务的清理逻辑。这样“连接建立”和“连接关闭”仍然成对出现， 而且建立失败会让 Fiber 进入 FAILED，不会留下半初始化状态。

命名与边界

  • 服务名是扁平的。 所有插件共享一个命名空间，tools、llm 这种普通名字很容易冲突，建议加前缀，如 myapp/store 不是合法标识符，通常用 myappStore 或 todoStore。
  • 一个名字只对应一个实现。 同一作用域重复注册会抛错；需要多实例就 isolate。
  • 服务不是全局单例。 它的生命周期跟着 Fiber 走；Fiber 卸载，服务就消失。
  • 服务适合“共享能力”，不适合“每次调用的数据”。 一次请求的上下文用参数传，不要塞进服务。
设计服务时问三个问题

① 这个能力需要被多个插件使用吗？② 它可能需要被替换实现吗？③ 它有需要释放的资源吗？ 三个里有一个“是”，就值得做成服务；如果都没有，一个普通函数或纯对象可能更合适。

本章小结

  • 服务 = 名字 + 约定 + 实现；消费者依赖名字，不依赖具体类。
  • Service 子类在构造函数里 super(ctx, name) 注册，生命周期归 Fiber。
  • 声明合并只负责类型，不生成运行时代码。
  • inject 是硬依赖，ctx.get 是可选依赖；两者对“提供者消失”的反应不同。
  • 替换提供者时，消费者会自动卸载并重载，代码不用改。
  • isolate 让同一服务名在多个分支里拥有不同实例。

自测一下

为什么消费者不应该 import 提供者的类？

因为那会在编译期把消费者绑定到某个具体实现，替换实现、测试替身、多租户隔离都会变得困难。 消费者应该只依赖服务名和服务定义（类型/接口），由装配层决定用哪个提供者。

super(ctx, 'db') 做了哪几件事？

它把当前实例注册为名为 db 的服务，记录所属 Fiber，并通过 Effect 绑定生命周期； 同时设置 this.ctx 和 this.name，让服务方法可以通过 this.ctx 使用其他服务。若服务是可调用形式，还会创建可调用的代理。

提供者被卸载后，消费者会怎样？如果希望它继续运行，应该怎么写？

如果消费者把 db 写在 inject 里，它会随之卸载，等服务恢复后再重载。 如果希望它继续运行，就不要 inject，改用 ctx.get('db') 并在每次使用时判断，同时接受“能力可能暂时不可用”的降级逻辑。
