Effect：注册即可撤销

Cordis 的所有魔法，最后都落在一句话上：注册是可逆的副作用。 定时器、监听器、服务、子插件，只要是通过 ctx 建立的，都应该能随着 Fiber 一起撤销。 这一章讲清楚“怎么撤销”和“为什么你总是漏掉一个”。

难度 入门 阅读 约 20 分钟 前置 第 5 章 关键词 disposer · 逆序 · 泄漏
本章你将学会
  • 用 ctx.effect() 管理 Cordis 不认识的资源；
  • 知道哪些 API 已经自动是 Effect，不需要你手写；
  • 理解卸载顺序，以及异步清理的并发陷阱；
  • 用“获取在 effect 内，释放在 disposer 里”消除大部分泄漏。

先看一个会泄漏的插件

这是一个“心跳”插件。它每 200 毫秒打印一次，看起来完全正常：

bad-heartbeat.tsts
import type { Context } from '@deepseek-ai/cordis'

export function apply(ctx: Context) {
  setInterval(() => console.log('tick'), 200)
}

正常运行时没有问题。但一旦插件被卸载——改配置、热更新、依赖消失——定时器仍然在跑。 再加载一次，就有两个定时器；再改一次，三个。控制台开始以 200 毫秒为单位刷屏， 而你已经在别的文件里找 bug 了。

正确的写法，是把“申请资源”和“释放资源”放在同一个 Effect 里：

good-heartbeat.tsts
import type { Context } from '@deepseek-ai/cordis'

export function apply(ctx: Context) {
  ctx.effect(() => {
    const timer = setInterval(() => console.log('tick'), 200)
    return () => {
      clearInterval(timer)
      console.log('heartbeat stopped')
    }
  })
}
类比 · 借书登记

借书时登记“我借了什么”，还书时按登记表逐条销账。Effect 就是那张登记表： 你不需要在离开图书馆时凭记忆回想借过哪些书，登记表会提醒你。

ctx.effect 的四种形态

ctx.effect(body) 会立刻执行 body，并收集它产生的 disposer。 body 可以返回四种东西：

返回值写法适合
一个函数 () => () => cleanup() 绝大多数同步资源：定时器、监听器、句柄。
函数的 Promise async () => { ...; return () => cleanup() } 需要先异步获取资源，再返回清理函数。
函数的同步迭代器 function* () { yield dispose1; yield dispose2 } 一个 effect 里管理多个资源，逐个登记。
函数的异步迭代器 async function* () { ... } 边异步初始化边登记清理，适合复杂资源。

日常开发中，前两种覆盖了九成场景。异步获取资源可以这样写：

async-effect.tsts
export function apply(ctx: Context) {
  ctx.effect(async () => {
    const connection = await connect()
    console.log('connected')

    return () => {
      connection.close()
      console.log('disconnected')
    }
  })
}
一个重要的保证

如果插件在 connect() 还没完成时就被卸载，Cordis 会等初始化完成，再调用清理函数， 而不是留下一个“连上了但没人关”的连接。这是 ctx.effect(async ...) 比手写 try/finally 更安全的地方。

这些注册已经自动是 Effect

你不需要给每个 API 都套一层 ctx.effect。Cordis 和 Harness 的注册类 API 已经把返回值接入了生命周期：

API卸载时自动撤销
ctx.on(event, listener)事件监听器
ctx.once(event, listener)一次性监听器
ctx.plugin(child)子插件及其整棵子树
ctx.provide(name, value)服务注册
new Service(ctx, name)服务注册（构造时自动完成）
ctx.logger.exporter(exporter)日志导出器
Harness 的 ctx.tools.register(...)工具注册（返回的 disposer 被接入 Fiber）

判断标准不是“这个 API 叫什么”，而是“它有没有把 disposer 交给 Cordis”。 一个设计良好的注册 API 应该返回 disposer；插件作者可以用 ctx.effect 把它接进来。

wrap-disposer.tsts
export function apply(ctx: Context) {
  // 假设某个第三方库返回了 remove 函数
  const remove = thirdParty.subscribe('event', handler)

  // 把它接入当前 Fiber 的生命周期
  ctx.effect(() => remove)
}

卸载顺序：逆序，但异步会并发

Effect 按注册顺序的逆序撤销。先申请的资源后释放，符合“后进先出”的直觉：

order.tsts
export function apply(ctx: Context) {
  ctx.effect(() => {
    console.log('A setup')
    return () => console.log('A cleanup')
  })

  ctx.effect(() => {
    console.log('B setup')
    return () => console.log('B cleanup')
  })
}
终端output
A setup
B setup
B cleanup
A cleanup

但有一个关键细节：多个 Effect 的异步清理会并发开始。Cordis 会同时调用它们的 disposer， 再一起等待，而不是等 A 完全关完再开始 B。

顺序敏感时怎么办

如果“先关 server，再关数据库”是硬性要求，不要依赖两个独立 Effect 的先后。把这两步放进同一个 disposer， 在里面按顺序 await；或者放进同一个 Effect 的生成器里，让它们作为一个整体撤销。 记住：逆序是启动顺序，不是完成顺序。

ordered-cleanup.tsts
ctx.effect(() => {
  const server = startServer()
  const db = connectDatabase()

  return async () => {
    await server.close()   // 先停入口
    await db.close()       // 再关依赖
  }
})

disposer 的调用与重复调用

ctx.effect 返回的 disposer 可以手动调用，用于“提前关闭某个功能”，而不必卸载整个插件。 重复调用是安全的：第一次之后就是 no-op。

manual-dispose.tsts
const dispose = ctx.effect(() => {
  const timer = setInterval(() => console.log('tick'), 1000)
  return () => clearInterval(timer)
})

dispose()
dispose() // 不会报错，也不会重复清理

disposer 可能是异步的（例如返回了 async () => ...）。此时它的返回值是一个 Promise， 卸载流程会等待它。如果你手动调用，记得 await，否则后续步骤可能在资源还没释放时就开始。

获取在 effect 内，释放在 disposer 里

这条规则听起来简单，却能消掉大部分泄漏：

做法结果
在 effect 外获取资源，effect 内只返回清理函数 获取失败时没有清理；获取成功但 effect 注册失败时会泄漏。
在 effect 内获取，在返回的 disposer 里释放 获取与释放成对；Cordis 能保证清理一定被调用。
把清理函数存到模块变量，等“合适的时候”调用 很容易忘记；热更新后变量指向旧实例，越积越多。
right-way.tsts
ctx.effect(() => {
  const watcher = fs.watch('./config', () => reload())
  return () => watcher.close()
})

如果资源获取本身是异步的，也把它放进 async effect，而不是先 await 再注册： 前者在卸载时能等初始化完成并清理，后者可能在 await 期间就被卸载，留下半成品。

用官方插件代替手写定时器

如果你经常需要定时器，Cordis 官方提供了 @deepseek-ai/cordis-plugin-timer。 它把 setInterval、setTimeout、节流、防抖都包装成了 Effect：

timer.tsts
export const inject = ['timer']

export function apply(ctx: Context) {
  ctx.interval(() => console.log('tick'), 1000)
  ctx.timeout(() => console.log('once'), 5000)
}

注意 inject: ['timer']：先声明依赖，再使用 ctx.interval。这比自己写 setInterval 再 clearInterval 更不容易漏，而且语义更清楚。

诊断：看看当前 Fiber 注册了什么

fiber.getEffects() 会返回当前仍然存活的 Effect 元数据树，包含标签和嵌套关系。 排查“到底是谁没清理”时很有用：

effects.tsts
export function apply(ctx: Context) {
  ctx.on('demo/event', () => {})
  ctx.effect(() => {
    const timer = setInterval(() => {}, 1000)
    return () => clearInterval(timer)
  }, 'demo heartbeat')

  console.log(ctx.fiber.getEffects())
}

输出里会看到类似 ctx.on("demo/event")、demo heartbeat 的标签。 框架内置的注册都有可读标签，自己写的 Effect 也建议传第二个参数命名。

五个常见错误

错误后果修正
只清理定时器，不清理它触发的监听器 监听器仍持有闭包，插件无法真正释放 把所有相关注册放进同一个 Effect
异步 disposer 没有 await 后续步骤在资源未释放时开始 在同一个 disposer 内按顺序 await
在已卸载的上下文里再注册 抛 INACTIVE_EFFECT，或注册到错误的 Fiber 注册集中在 apply 阶段；异步回调先检查状态
模块级保存资源句柄 热更新后旧句柄泄漏，新实例拿不到 句柄放在插件闭包里，随 Fiber 走
清理函数里再做耗时业务 卸载被拖慢，父插件等待 清理只做“释放”，业务动作另行安排
Effect 不是万能的

如果第三方库自己在全局注册了单例、或者在内部启动了无法关闭的线程，ctx.effect 也救不了。它只能管理“你能拿到 disposer”的资源。遇到这种情况，要么换库，要么把整个进程作为生命周期边界。

本章小结

  • Effect 是“可撤销的注册”：body 立即执行，返回的 disposer 在卸载时执行。
  • 支持同步函数、Promise、同步/异步迭代器；异步初始化会先完成再清理。
  • ctx.on、ctx.plugin、provide、Service 等已经是 Effect，不必重复包装。
  • 卸载按注册逆序开始，但多个异步 disposer 并发完成；顺序敏感时放进同一个 disposer。
  • 获取资源在 effect 内，释放资源在 disposer 里；不要依赖模块级变量。
  • Effect 只能管理拿得到 disposer 的资源；无法关闭的全局状态仍然是边界。

自测一下

为什么“在 effect 外获取资源、effect 内返回清理函数”不够好？

因为获取可能失败，也可能在获取成功之后、Effect 注册之前发生异常或卸载，导致资源没有被登记， 清理函数永远不会被调用。正确做法是把获取也放进 effect body，保证“获取成功”与“登记清理”是同一个动作。

两个 Effect 的清理都是异步的，Cordis 会等第一个完成再开始第二个吗？

不会。它会按逆序启动，但多个异步 disposer 会并发执行，然后一起等待。 如果必须串行，请把步骤放进同一个 disposer，并在其中依次 await。

一个插件只注册了 ctx.on(...)，没有写 ctx.effect。卸载时会泄漏吗？

不会。ctx.on 内部已经把监听器注册为当前 Fiber 的 Effect，卸载时会自动移除。 这也是为什么应该优先使用框架提供的注册 API，而不是自己操作底层事件发射器。
