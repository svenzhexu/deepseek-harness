事件：互不相识也能协作

服务适合“我需要调用一个能力”，事件适合“发生了一件事，关心的人自己来处理”。 前者是点对点，后者是广播。Cordis 在广播之上又加了顺序、并发、短路和中间件， 让事件不只是“通知”，还能表达策略。

难度 入门 阅读 约 30 分钟 前置 第 6 章 关键词 分发模式 · waterfall · 短路
本章你将学会
  • 用声明合并定义类型安全的事件；
  • 区分 emit、parallel、serial、bail、waterfall 五种分发模式；
  • 写出正确的 waterfall 中间件，知道什么时候必须调用 next()；
  • 避免“异步监听器没被等待”和“忘记 next 吞掉下游”这两个大坑。

为什么需要事件

假设每次新增待办，都要更新统计。最直接的做法是在新增逻辑里调用统计服务：

没有事件ts
async function addTodo(title: string) {
  const todo = await store.add(title)
  await stats.record('todo_added')   // 新增逻辑必须知道统计器
  await notifier.push('new todo')    // 还要知道通知器
  return todo
}

每多一个“关心新增”的功能，addTodo 就要多一行。它从业务函数变成了“所有副作用的调度中心”， 而且每加一个功能都要改它、重新测试它。

用事件改写后，新增逻辑只负责“宣布这件事发生了”：

有事件ts
async function addTodo(title: string) {
  const todo = await store.add(title)
  ctx.emit('todo/added', todo)       // 谁关心，谁自己来听
  return todo
}

统计器、通知器、审计日志各自订阅 todo/added，新增逻辑不需要认识它们。 这就是发布 / 订阅：生产者只负责发布，消费者只负责订阅，双方通过事件名相遇。

声明一个事件

Cordis 的事件是类型化的。和给 Context 加服务一样，用声明合并给 Events 接口加成员：

events.d.ts（或任意被导入的 .ts）ts
declare module '@deepseek-ai/cordis' {
  interface Events {
    'todo/added'(todo: { title: string; done: boolean }): void
    'todo/completed'(todo: { title: string; done: boolean }): void
  }
}

成员签名里的参数，就是监听器收到的参数；返回值就是分发方法能拿到的值。事件名只是字符串， 但声明合并让它获得了完整的类型检查：写错名字、少传参数、用错分发方式，编辑器都会提醒。

命名约定

推荐使用 命名空间/动作 的形式，例如 todo/added、tools/result、 approval/request。扁平的事件名空间很容易冲突，前缀能让来源一目了然。 internal/ 开头的事件由框架使用，插件不要占用。

发送与监听

下面是一个完整例子：StatsService 在计数变化时发出事件，根上下文上的监听器负责打印。

stats.tsts
import { Context, Service } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    stats: StatsService
  }
  interface Events {
    'stats/report'(name: string, count: number): void
  }
}

class StatsService extends Service {
  private counts = new Map<string, number>()

  constructor(ctx: Context) {
    super(ctx, 'stats')
  }

  bump(name: string) {
    const next = (this.counts.get(name) ?? 0) + 1
    this.counts.set(name, next)
    this.ctx.emit('stats/report', name, next)
  }
}

const root = new Context()
await root.plugin(StatsService)

root.on('stats/report', (name, count) => {
  console.log(`[stats] ${name} -> ${count}`)
})

root.stats.bump('tool_call')
root.stats.bump('tool_call')
root.stats.bump('prompt')
终端output
[stats] tool_call -> 1
[stats] tool_call -> 2
[stats] prompt -> 1

ctx.on() 返回一个移除监听器的函数，同时它本身也是一个 Effect：所属 Fiber 卸载时， 监听器自动移除，不需要手动 removeListener。如果只想监听一次，用 ctx.once()。

五种分发模式

同一个事件，可以用五种方式分发。选哪一种不是风格问题，而是事件契约的一部分： 监听器能不能返回值、能不能并发、能不能短路，都由它决定。

模式调用是否等待顺序 / 返回值适合
emit ctx.emit(name, ...args) 否 按注册顺序同步调用；忽略返回值与 Promise。 纯通知：日志、统计、刷新 UI。
parallel await ctx.parallel(...) 是 全部并发；等所有监听器结束；任一出错抛 AggregateError。 多个独立的异步副作用，需要全部完成。
serial await ctx.serial(...) 是 按顺序逐个等待；第一个“命中值”停止并返回。 优先级链：前面的处理者可以先接管。
bail ctx.bail(...) 否 同步版 serial；第一个命中值停止并返回。 同步的“谁能处理就谁处理”。
waterfall ctx.waterfall(name, ...args, next) 否（由调用方 await） 环绕中间件：调用 next() 委托，返回值可被逐层包装；不调用则短路。 拦截、改写、否决一个决策。

“命中值”的定义是：不是 null、不是 false、也不是 undefined。 注意 0 和空字符串 '' 都算命中；如果你需要表达“未处理”，请返回 null 或 undefined，不要返回 false 然后期待它继续。

选择哪一种？

  • 只是“通知一下”，没人需要回值 → emit；
  • 多个异步副作用都要完成，缺一不可 → parallel；
  • 按优先级依次询问，先能处理的赢 → serial（异步）或 bail（同步）；
  • 需要“包住”一个决策，改写输入/输出，或者直接否决 → waterfall。

waterfall：洋葱一样的中间件

waterfall 是 Cordis 最强大、也最容易用错的模式。每个监听器收到原始参数和一个 next()： 调用 next() 会把控制权交给下一个监听器，最后是调用方传入的默认逻辑 （也就是 ctx.waterfall 的最后一个参数）；不调用就直接返回，则表示“我接管了，后面的不用执行”。

listener 1 → 调用 next() → listener 2 → 调用 next() → 默认行为
← 包装返回值 ← listener 1 ← 包装返回值 ← listener 2 ← 返回结果 默认行为
waterfall.tsts
import { Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Events {
    'demo/transform'(input: string, next: () => Promise<string>): Promise<string>
  }
}

const root = new Context()

// 监听器 1：包装下游结果
root.on('demo/transform', async (input, next) => {
  const downstream = await next()
  return downstream.toUpperCase()
})

// 监听器 2：拥有决定权时短路
root.on('demo/transform', async (input, next) => {
  if (input.includes('blocked')) return '** blocked **'
  return next()
})

console.log(await root.waterfall('demo/transform', 'hello', async () => 'hello'))
console.log(await root.waterfall('demo/transform', 'blocked words', async () => 'blocked words'))
终端output
HELLO
** BLOCKED **

第二行为什么是大写？把调用过程拆开看：

  1. 监听器 1 先运行，调用 next()，进入监听器 2；
  2. 监听器 2 看到 blocked，直接返回，没有调用 next()；
  3. 于是最内层的默认函数没有执行，返回的是 '** blocked **'；
  4. 监听器 1 拿到这个返回值，执行 toUpperCase()，变成 '** BLOCKED **'。
最重要的一条纪律

只观察、只记录、只标注的 waterfall 监听器，必须调用 next()。 如果忘了，它会静默吞掉所有下游行为——没有报错，没有日志，默认逻辑就是不执行。 这是 Cordis 项目里最隐蔽的 bug 之一。

prepend：插到最前面

默认按注册顺序，先注册的在外层。如果你必须在所有普通监听器之前运行（例如强制审计、安全策略）， 可以用 prepend：

prepend.tsts
root.on('demo/transform', async (input, next) => {
  console.log('always first')
  return next()
}, { prepend: true })

// 简写：root.on(name, listener, true)

不要习惯性地加 prepend。它会让你的监听器绕过正常的注册顺序，多个插件都这么做时， 顺序会变得难以推理。只有“必须早于所有人”的语义才值得使用。

异步与错误

这是第二个大坑：emit 不会等待监听器返回的 Promise。 下面这段代码看起来会依次打印，实际上 after 很可能先出现：

emit-async.tsts
declare module '@deepseek-ai/cordis' {
  interface Events {
    'demo/async'(): void
  }
}

root.on('demo/async', async () => {
  await new Promise(resolve => setTimeout(resolve, 100))
  console.log('listener done')
})

root.emit('demo/async')
console.log('after emit')
终端output
after emit
listener done

如果必须等所有异步监听器完成，用 await ctx.parallel(...)；如果必须按顺序等待， 用 await ctx.serial(...)。不要用 emit 然后期待 Promise 被收集。

场景行为
emit 的监听器同步抛错异常向调用方传播，后续监听器不再执行。
emit 的监听器返回 rejected Promise不会被等待，可能成为未处理的 Promise rejection。
parallel 中任一监听器抛错等待所有结束后，抛出包含全部错误的 AggregateError。
serial / bail 中抛错立即向调用方传播，后续监听器不执行。
waterfall 中抛错向调用方传播；已经进入的下游不会自动回滚。

事件还是服务？

问题用服务用事件
我需要一个确定的能力是否
我需要一个返回值是可以（serial / waterfall），但更绕
我想让多个互不相识的插件都知道否是
我想允许插件改写或否决一个决策不适合是（waterfall）
我关心“谁在监听”吗关心提供者不关心

经验法则：直接调用能力用服务，传播事实或插入策略用事件。 如果你发现自己在事件监听器里到处找返回值、拼装复杂的结果，可能它本来就应该是一个服务方法。

四个常见错误

错误后果修正
waterfall 监听器忘记 next() 下游与默认行为被静默跳过 只观察就 return next()；要否决才直接返回
用 emit 触发异步工作 调用方以为完成了，实际还在跑 改 parallel / serial 并 await
事件名没有命名空间 与别的插件冲突，监听器收到意外事件 用 yourApp/action 形式
在监听器里做耗时同步计算 阻塞所有后续监听器与调用方 拆成异步任务，或改为队列 / 后台 job
调试事件的好习惯

遇到“事件没反应”，先确认三件事：事件名拼写一致吗？声明合并被导入到了吗（类型不对不一定影响运行，但说明模块没加载）？ 监听器是在事件发出之前注册的吗？emit 不保留历史，错过就是错过。

本章小结

  • 事件用于广播事实；服务用于直接调用能力，两者解决不同问题。
  • 用 interface Events 声明事件名与签名，获得完整类型检查。
  • 五种模式：emit / parallel / serial / bail / waterfall，选择取决于“是否等待、是否有返回值、是否短路”。
  • waterfall 是环绕中间件；next() 委托，不调用则短路；观察型监听器必须调用。
  • emit 不等待异步监听器；需要等待就用 parallel 或 serial。
  • ctx.on 是 Effect，监听器随插件自动移除。

自测一下

“通知所有插件刷新缓存”应该用哪种分发模式？为什么？

如果刷新是异步的、且需要等全部完成，用 parallel；如果只是发个通知、不关心完成时间，用 emit。 关键是明确“调用方是否需要等待”。用 emit 触发异步刷新，会让调用方误以为缓存已经更新。

waterfall 中，一个只做日志的监听器直接 return 而不调用 next()，会发生什么？

链条在这里短路：后续监听器和最内层的默认行为都不会执行，而且通常没有任何报错。 这就是“观察型监听器必须调用 next()”的原因。

serial 的监听器返回 false，会停止后续监听器吗？

不会。false、null、undefined 都被视为“未命中”，会继续执行。 要短路，请返回一个非 false / 非空的值，例如 true、对象或字符串。
