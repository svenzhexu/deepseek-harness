配置与 Loader

到上一章为止，所有插件都是我们在 main.ts 里手动挂载的。真实应用往往需要“换一台机器就换一套配置”、 “让用户自己开关功能”、“改一行配置不重启”。这一章介绍 Cordis 的可选装配层：Loader 与 cordis.yml。

难度 进阶 阅读 约 35 分钟 前置 第 6、8 章 关键词 schema · Entry · Include · HMR
本章你将学会
  • 用 schema 声明插件配置，并让错误配置在启动时失败；
  • 读懂 cordis.yml 的每个字段；
  • 用 Loader + Include 把文件变成运行中的插件树；
  • 用分组、隔离、禁用与 HMR 管理复杂组合。

为什么把装配放进文件

手动挂载插件并没有错，它清晰、可调试，适合小应用和测试。但当“装哪些插件、各自什么配置”变成部署差异时， 写死在代码里就开始碍事：

场景写死在 main配置驱动
开发 / 生产用不同数据库改代码或加环境变量分支换一份 yml / 覆盖一行配置
用户想关闭某个功能改代码重新发版disabled: true
插件加载失败要定位读 main 的调用顺序看 Entry 的 id 与状态
运行中改配置重启进程Include 自动重读并更新
第三方扩展改 main 的源码往 yml 里加一行

注意：配置文件不是“把代码变成魔法”。它仍然只是声明“装哪个模块、传什么参数”， 真正的逻辑、依赖和清理，仍然由插件自己负责。

给插件加配置：schema

插件通过导出一个 Config 来声明自己的配置结构。Cordis 支持任意 Standard Schema 验证器； 本仓库配套使用的是 Schemastery。

config-demo.tsts
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'

export const name = 'config-demo'

export interface Config {
  greeting: string
  targets: string[]
}

export const Config: Schema<Config> = Schema.object({
  greeting: Schema.string().default('Hello'),
  targets: Schema.array(String).default(['world']),
})

export function apply(ctx: Context, config: Config) {
  for (const target of config.targets) {
    console.log(`${config.greeting}, ${target}!`)
  }
}

这里有两个同名的 Config：一个是 TypeScript 接口（给编译期用），一个是运行时 schema（给 Cordis 用）。 名字相同是约定，不是语法要求；关键是导出名为 Config 的 schema。

cordis.ymlyaml
- id: config-demo
  name: './config-demo.ts'
  config:
    targets: ['alpha', 'beta']
终端output
Hello, alpha!
Hello, beta!

没有提供 greeting，schema 的默认值把它补齐了。所以 apply 里拿到的 config 永远是“完整且经过校验”的，不需要写 config.greeting ?? 'Hello'。

配置错误要明确失败

把 targets 写成字符串，再运行：

cordis.yml（错误示例）yaml
- id: config-demo
  name: './config-demo.ts'
  config:
    targets: 'not-an-array'
终端output
ValidationError: invalid config:
  - $.targets expected array but got not-an-array (at targets)

Fiber 进入 FAILED，宿主通常会打印错误并退出。这就是“misconfiguration fails loud”： 配置错误在启动时暴露，而不是运行到一半才崩。

cordis.yml 解剖

一个 Cordis 配置文件是一个顶层数组，每个元素是一个 Entry（条目），描述“加载哪个模块、传什么配置”。 最小的条目只有两行：

cordis.ymlyaml
- name: './hello.ts'

完整的条目可以带更多字段：

cordis.ymlyaml
- id: store
  name: './plugins/store.ts'
  config:
    file: './data.json'

- id: cli
  name: './plugins/cli.ts'
  inject: ['store']

- id: experimental
  name: './plugins/experimental.ts'
  disabled: true
字段作用细节
id 条目的稳定标识。 用于比较“改配置”与“删了再加”。省略时会生成随机 id，文件一改就可能被当成新条目重新挂载。
name 模块说明符。 相对路径（相对配置文件或 baseUrl）或包名；本仓库还支持 cordis:group 这类内置名。
config 传给插件的配置对象。 启动前由插件 schema 校验；默认值会补齐。
group 标记这是一个“组”，其 config 是子条目数组。 与 name: cordis:group（或 Group 插件）配合，见下文。
disabled 不加载这个条目。 条目保留在文件里；改回 false 后会重新加载。
inject 在配置层追加依赖或 intercept 配置。 通常由插件自己声明；条目级 inject 用于覆盖部署差异。
isolate 为该条目创建或加入服务隔离域。 { db: true } 独立域；{ db: 'team-a' } 共享命名域。
intercept 为该条目覆盖服务配置。 只对声明了服务配置类型的服务生效。
顺序无关

条目在数组里的位置不决定加载先后。所有条目会并发启动，真正的顺序由 inject 依赖推导。唯一需要关心顺序的地方是“谁先出现在文件里更好读”，而不是“谁先启动”。

Loader 如何把文件变成插件树

Loader 本身也是一个 Cordis 插件。它维护一棵 EntryTree，每个 Entry 对应配置文件里的一行。 Include 则负责“读文件”，把 YAML 解析成条目数组。

cordis.yml顶层数组
→
Include解析 YAML / JSON，应用 patch
→
EntryTree按 id 维护条目
→
import()加载模块
→
ctx.plugin()创建 Fiber

仓库里的启动器只有十几行，它做的事情就是“创建根上下文 → 挂 Loader → 让 Include 读文件”：

vendor/cordis/bin.jsjs
import { Context } from '@deepseek-ai/cordis'
import { pathToFileURL } from 'node:url'
import Loader from '@deepseek-ai/cordis-plugin-loader'

const ctx = new Context()
ctx.baseUrl = pathToFileURL(process.cwd()).href + '/'

await ctx.plugin(Loader)
await ctx.loader.create({
  name: '@deepseek-ai/cordis-plugin-include',
  config: {
    path: './cordis.yml',
  },
})

ctx.baseUrl 决定了 './hello.ts' 这类相对路径从哪里解析。 启动器把它设为当前工作目录，所以你在哪个目录运行，就在哪个目录找配置和插件。

最小可用命令

在 tmp/cordis-tutorial 这类目录里，执行 node --import tsx ../../vendor/cordis/bin.js 即可。它不需要你先编译 TypeScript， tsx 会在导入时转译。

分组：把一组条目当作一个单元

当插件多起来，你会希望“这一组是 Web 服务”、“那一组是实验功能”，可以整体启用、禁用、隔离。 组条目长这样：

cordis.ymlyaml
- id: web
  name: '@deepseek-ai/cordis-plugin-group'
  group: true
  isolate:
    db: 'web-team'
  config:
    - id: server
      name: './plugins/server.ts'
      config:
        port: 3000

    - id: api
      name: './plugins/api.ts'
      inject: ['db']

组的 config 不是普通对象，而是子条目数组。组内条目共享组的上下文，包括 isolate 指定的作用域；组卸载时，子条目会一起卸载。

在 DeepSeek Harness 的 profile 里，常把 cordis:group 注册为内置名，写法更短： name: cordis:group。独立项目里如果没有注册内置名，就写 Group 包的完整名称。

隔离与拦截：在配置层表达部署差异

第 6 章我们用 ctx.isolate('db') 在代码里创建作用域。Loader 把这个能力搬到了配置里：

tenants.ymlyaml
- id: tenant-a
  name: '@deepseek-ai/cordis-plugin-group'
  group: true
  isolate:
    db: true
  config:
    - id: db
      name: './plugins/db.ts'
      config: { file: './a.json' }
    - id: app
      name: './plugins/app.ts'

- id: tenant-b
  name: '@deepseek-ai/cordis-plugin-group'
  group: true
  isolate:
    db: true
  config:
    - id: db
      name: './plugins/db.ts'
      config: { file: './b.json' }
    - id: app
      name: './plugins/app.ts'

两个租户各自看到自己的 db，互不覆盖。若希望它们共享同一个隔离域，把 true 换成同一个字符串标签即可，例如 db: 'shared'。

intercept 则用于“同一个服务，不同配置”。例如让某个组里的日志更安静：

intercept.ymlyaml
- id: quiet
  name: '@deepseek-ai/cordis-plugin-group'
  group: true
  intercept:
    logger:
      level: 0
  config:
    - name: './plugins/noisy.ts'

记住区分：isolate 换实现，intercept 改配置。 两者都只影响该条目及其子树。

disabled 与 !!js：让配置适应环境

disabled 是最简单的开关。它保留条目、停止加载；改回 false 就会重新加载， 依赖它的插件也会恢复。

本仓库的 Include 还支持 !!js 表达式，让配置在加载时计算。它只能出现在 config 和条目的 disabled 字段里：

env.ymlyaml
- id: demo
  name: './plugins/demo.ts'
  disabled: !!js process.env.NODE_ENV === 'test'
  config:
    greeting: !!js process.env.DEMO_GREETING ?? 'Hello'

config 里的表达式在插件自己的上下文中求值；disabled 在每次挂载决策时、 基于 Loader 上下文求值。其他字段（name、id、inject 等）保持字面值。

安全提醒

!!js 本质上是执行配置文件里的代码。只加载你信任的配置文件； 不要把用户上传的 YAML 直接交给 Include。需要“用户可配置”时，用 schema 限制字段，而不是开放任意表达式。

HMR：改代码不用重启

HMR（Hot Module Replacement，热模块替换）不是独立魔法，而是“卸载旧插件、加载新插件”的自动化： 文件监听器发现变化 → 找到受影响的 Entry → 卸载对应 Fiber → 清除模块缓存 → 重新导入 → 重新挂载。

hmr.ymlyaml
- id: logger
  name: '@deepseek-ai/cordis-plugin-logger-console'

- id: timer
  name: '@deepseek-ai/cordis-plugin-timer'

- id: hmr
  name: '@deepseek-ai/cordis-plugin-hmr'
  config:
    root: ['.']
    debounce: 100

- id: hello
  name: './hello.ts'

编辑 hello.ts 并保存，终端会出现类似：

终端output
hello from my first plugin
[I] hmr watching [ '.' ]
[I] hmr reload plugin at hello.ts
hello from my EDITED plugin

旧实例先卸载（所有 Effect 回卷），新代码再加载，apply 重新执行。 如果某个插件没有正确清理，HMR 会立刻把它暴露出来：定时器翻倍、监听器重复、连接泄漏。 所以HMR 既是开发工具，也是对 Effect 纪律的测试。

HMR 的运行要求

@deepseek-ai/cordis-plugin-hmr 需要 Loader、Timer，以及能访问 Node 内部模块加载器的运行时； 缺少这些条件时它会直接报错。DeepSeek Harness 的启动器已经处理了这些前提；它还提供了自己的 @deepseek-ai/dsh-hmr，概念相同、配置项略有差异。独立项目里如果配置不成功， 先回到“手动重启”，不要卡在 HMR 上。

修改 cordis.yml 本身也会触发更新：Loader 按 id 比较条目，只挂载、卸载或重新配置变化的部分。 这也解释了为什么建议给每个条目写稳定的 id。

六种常见失败

现象可能原因处理
条目完全没反应 模块名拼错、路径不对、包没安装。 看 logger 的 error；Loader 对“无法解析”通常只记录日志，不崩溃。
启动即报 ValidationError config 与 schema 不匹配。 按错误里的字段路径修正；不要绕过 schema。
插件停在 PENDING inject 的服务没人提供，或提供者被 disabled。 检查条目列表与 disabled；用第 5 章的诊断脚本。
服务重复注册 两个条目提供了同名服务，且没有隔离。 给其中一个加 isolate，或改用不同服务名。
改了配置没生效 条目没有稳定 id，或被当成新条目；文件没保存/监听未启动。 补 id；确认 Include 的监控与文件路径。
YAML 解析失败 缩进错误、顶层不是数组、重复 key。 先修 YAML；Include 会拒绝非数组的顶层结构。
进阶 · volatile 配置

有些配置字段会被插件在每次操作中读取，例如提示词、阈值。Schemastery 的 .volatile() 可以把它们变成稳定引用，通过 .get() 读取；Loader 发现只有这些字段变化时，会直接更新引用并发出 loader/volatile-update，而不重启插件。它适合“频繁微调、重启代价高”的字段；普通字段变化仍然走 完整的卸载/重载流程。

本章小结

  • 配置是插件契约的一部分：用 schema 校验，默认值补齐，错误在启动时明确失败。
  • cordis.yml 是顶层数组；每个条目描述模块、配置、依赖、开关、隔离。
  • Loader 维护 EntryTree，Include 负责读文件；它们都是可选的外围插件。
  • id 稳定才能正确比较“修改”与“重建”；条目顺序不影响启动顺序。
  • 组用于整体管理子树；isolate 换实现，intercept 改配置。
  • HMR 是“卸载 + 重载”的自动化，前提是每个插件都能正确清理。

自测一下

为什么 cordis.yml 里两个条目的先后顺序不影响加载？

因为 Loader 会并发创建所有条目，插件是否启动由 inject 依赖决定：缺依赖就 PENDING， 依赖就绪再 ACTIVE。顺序由关系推导，而不是数组位置。

isolate: { db: true } 和 isolate: { db: 'team-a' } 有什么区别？

true 为该条目创建一个独立的本地作用域，只影响它和它的子树； 'team-a' 则加入名为 team-a 的共享作用域，多个使用同一标签的条目会看到同一个 db 实现。

HMR 为什么能工作？它对插件作者提出了什么要求？

因为 Cordis 的生命周期是可逆的：卸载会撤销插件注册的所有 Effect，加载会重新执行插件。 HMR 只是监听文件变化并触发这一过程。它要求插件把定时器、监听器、连接等资源都登记为 Effect； 否则旧实例的残留会泄漏，热更新越多次越严重。
