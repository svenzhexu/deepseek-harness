速查表与排错手册

这一章不需要从头读。写代码时忘了 API，遇到看不懂的报错，或者想快速复习术语，回来查即可。 最后有 10 道综合自测题和一份下一步路线。

API 速查

Context

写法作用备注
new Context()创建根上下文内置 Registry、Reflect、Events、Logger。
ctx.plugin(plugin, config?)挂载插件，返回 Fiber可 await；启动错误会抛出。
ctx.get(name, strict?)可选取服务找不到返回 undefined。
ctx.provide(name, value)注册服务返回 disposer；随 Fiber 卸载。
ctx.set(name, value)更新自己提供的服务只有提供者 Fiber 能改。
ctx.isolate(name, label?)创建服务隔离作用域同一 label 共享作用域。
ctx.intercept(name, config)覆盖服务配置服务需声明配置类型。
ctx.extend(meta?)创建子上下文子继承父，父不受影响。
ctx.on / once / emit事件监听与分发on 返回 disposer。
ctx.parallel / serial / bail / waterfall其他分发模式见第 7 章。
ctx.effect(body, label?)注册可撤销副作用body 立即执行，返回 disposer。
ctx.accessor(name, options)定义计算属性框架内部使用较多。

Fiber

成员作用
fiber.statePENDING / LOADING / ACTIVE / FAILED / UNLOADING / DISPOSED
fiber.name沿父链得到的显示名，根为 'root'。
fiber.uid注册表编号；卸载后为 null。
fiber.ctx该插件运行所在的子上下文。
await fiber等待启动稳定；失败时抛出错误。
fiber.dispose()卸载自身与子树，等待清理完成。
fiber.update(config)校验并应用新配置，随后重启。
fiber.restart()用当前配置卸载再加载。
fiber.getEffects()返回当前 Effect 元数据树，诊断用。

Service

写法作用
class X extends Service定义一个服务插件。
super(ctx, 'name')注册服务；名字进入扁平命名空间。
[Service.init]()构造函数之后的异步初始化；可返回 disposer。
[Service.check]()可用性判断；返回 false 时依赖者继续等待。
[Service.invoke](...)让服务本身可调用，例如 ctx.logger()。
[Service.config]声明服务接受的 intercept 配置类型。

Loader

写法作用
await ctx.plugin(Loader)挂载 Loader 服务。
ctx.loader.create(options)新增并启动一个条目，返回 id。
ctx.loader.update(id, options)更新、移动或重启条目。
ctx.loader.remove(id)停止并删除条目。
ctx.loader.resolve(id)按 id 查找条目，支持 a:b 嵌套。
ctx.loader.await()等待所有导入与重载完成。
ctx.loader.locate(fiber?)查找 Fiber 所属的条目 id。

cordis.yml 条目

字段类型作用
idstring稳定标识；省略会随机生成。
namestring模块名或相对路径。
configany传给插件的配置，启动前校验。
groupboolean标记为组，config 是子条目数组。
disabledboolean保留条目但不加载。
injectstring[] / object配置层追加依赖。
isolateobject为条目创建/加入服务隔离域。
interceptobject为条目覆盖服务配置。

生命周期一页纸

PENDINGinject 未满足
→
LOADING校验配置 + 执行插件
→
ACTIVE服务可用
→
UNLOADING逆序清理
→
DISPOSED不可重启

LOADING 失败 → FAILED；ACTIVE 时依赖消失或配置更新 → UNLOADING → 重新 LOADING。

阶段发生了什么插件代码在做什么
创建ctx.plugin() 创建 Fiber，记录原始配置与 inject。尚未执行。
等待逐个检查依赖是否可用。尚未执行。
加载解析配置、校验 schema、调用插件。apply 运行，注册服务/事件/Effect。
就绪状态变 ACTIVE，通知依赖者。正常处理业务。
卸载撤销 Effect、释放服务、通知依赖者。disposer 运行。

报错与现象对照

你看到的含义怎么修
cannot get property "x" without inject 读了一个不在祖先链上、也没 inject 的服务。 把 x 加进 inject；或改用 ctx.get('x')。
cannot get required service "x" in inactive context 依赖的服务当前不可用，常见于卸载后或异步回调里。 不要在 Fiber 卸载后访问服务；检查异步任务是否被正确取消。
service "x" has been registered at <...> 同一作用域重复注册同名服务。 改服务名，或给其中一个分支加 isolate。
property "x" is already declared as accessor 服务名与计算属性冲突。 换名字；检查是否有 ctx.accessor('x', ...)。
invalid plugin, expect function or object with an "apply" method 传给 ctx.plugin 的东西不是合法插件。 检查导出方式：模块默认导出、命名导出 apply，或类。
invalid config: 加字段路径 配置未通过 schema 校验。 按提示修字段；不要绕过校验。
cannot create effect on inactive context 在已卸载的上下文里注册 Effect。 注册集中在 apply 阶段；异步回调里先判断 Fiber 是否仍存活。
config file must be a top-level array of entries YAML 顶层不是数组，或文件为空/截断。 顶层写成 - name: ... 的列表；检查缩进。
cannot resolve entry "x" Loader 找不到该 id。 检查 id 拼写；嵌套条目用 parent:child。
--expose-internals is required for HMR service HMR 拿不到 Node 内部模块加载器。 用支持该能力的启动器；或暂时关闭 HMR。
代码没输出，也不报错 最常见是 PENDING；也可能是模块没解析、条目 disabled。 枚举 Fiber 状态；检查 inject 提供者、模块名、disabled。
事件监听器没反应 事件在监听器注册前就发出了，或名字不一致。 先注册再 emit；用声明合并检查名字；确认模块已加载。

七步调试清单

  1. 它加载了吗？ 枚举 ctx.registry.values()，看 Fiber 是否存在。
  2. 它是什么状态？ PENDING 找依赖；FAILED 找错误；DISPOSED 说明已被卸载。
  3. 依赖有人提供吗？ 搜 provide('name') 或 super(ctx, 'name')；注意拼写与大小写。
  4. 作用域对吗？ 提供者与消费者是否在同一个 isolate 分支。
  5. 配置过了吗？ 看 ValidationError；检查 config 字段类型与默认值。
  6. 代码执行到了吗？ 在 apply 第一行打日志；没有日志说明卡在前面。
  7. 是异步问题吗？ emit 不等待 Promise；waterfall 忘记 next() 会短路。
debug.tsts
import { FiberState, type Context } from '@deepseek-ai/cordis'

const NAMES = ['PENDING', 'LOADING', 'ACTIVE', 'FAILED', 'DISPOSED', 'UNLOADING']

export function apply(ctx: Context) {
  setTimeout(() => {
    console.log('--- fibers ---')
    for (const runtime of ctx.registry.values()) {
      for (const fiber of runtime.fibers) {
        console.log(fiber.name, NAMES[fiber.state], fiber.uid)
      }
    }
    console.log('--- effects ---')
    console.log(ctx.fiber.getEffects())
  }, 1000)
}

10 道综合自测

1. ctx.foo 与 ctx.get('foo') 的核心区别是什么？

属性访问是强依赖：对不在祖先链上的服务，插件上下文中要求先 inject，找不到会抛错； get 是可选取值，不要求 inject，找不到返回 undefined。

2. 插件停在 PENDING 和停在 FAILED，排查方向有什么不同？

PENDING 是“依赖没齐”，查 inject 列表、提供者是否存在、作用域是否一致； FAILED 是“执行出错”，查配置校验和 apply 抛出的异常。

3. 为什么 waterfall 的观察型监听器必须调用 next()？

因为不调用就表示短路，后续监听器和最内层默认行为都不会执行，而且不会报错。 只做日志、标注的监听器应当 return next()。

4. ctx.emit 会等待异步监听器吗？如果不会，应该用什么？

不会。需要等待全部异步监听器时用 await ctx.parallel； 需要按顺序等待时用 await ctx.serial。

5. 为什么每个注册都需要 disposer？没有会怎样？

因为插件会被卸载、替换、热更新。没有 disposer，注册会残留，造成定时器叠加、监听器重复、 连接泄漏，甚至访问已释放的服务。

6. 替换服务提供者时，消费者为什么不用改？

因为消费者依赖的是服务名，不是具体类。提供者消失时消费者被卸载，新提供者上线后消费者重新加载， 整个过程由 Cordis 的依赖跟踪完成。

7. isolate 和 intercept 分别改什么？

isolate 改“服务解析到哪个实现”，intercept 改“同一个实现读到的配置”。

8. 不用 Loader，Cordis 还能用吗？损失了什么？

能。直接 ctx.plugin() 即可。损失的是配置驱动装配、条目级禁用/分组、配置热更新， 以及基于文件变化的 HMR。

9. 配置 schema 应该由谁声明？为什么不能在 apply 里临时判断？

由插件自己声明（导出 Config），因为只有提供者知道合法输入。 在 apply 里临时判断会让错误暴露得太晚，也无法给 Loader 和配置工具提供结构信息。

10. 子插件和父插件的卸载顺序是什么？为什么？

父插件卸载会一并卸载子插件，并等待子插件清理完成。具体先后遵循 Effect 的逆序规则， 不要把“子一定先于父”当成固定保证；需要严格顺序时，把步骤放进同一个 disposer 显式 await。

下一步：读源码与做练习

到这里，你已经能读懂大部分 Cordis 项目了。想继续深入，建议按下面的顺序读源码——它比文档更精确， 而且这个仓库里的源码带有完整的 JSDoc：

顺序文件看什么

2vendor/cordis/src/registry.ts三种插件形态如何归一，Fiber 如何创建。
3vendor/cordis/src/fiber.ts状态机、依赖 epoch、Effect 收集与卸载。
4vendor/cordis/src/events.ts五种分发模式与监听器注册。

6vendor/cordis/src/service.tsService 基类与配置合并。
7vendor/loader/src/EntryTree、Entry、Group、隔离。

五个练习

  1. 给 todo 加删除：新增 remove 方法、todo/removed 事件和 CLI 分支。
  2. 写第二个存储 provider：用内存 Map 实现同样的接口，在 yml 里切换。
  3. 加 JSON 输出：todo list --json，只在 CLI 层处理，不影响服务。
  4. 测试事件：在测试里监听 todo/added，断言服务确实发出了事件。
  5. 加入 HMR：按第 9 章配置，改一行提示语，观察插件重载；再故意不清理定时器，观察泄漏。

最后记住三句话

  • 插件描述贡献，Context 负责寻址，Fiber 负责生命周期。
  • 服务用于直接调用，事件用于广播；注册的都要能撤销。
  • 先用最简单的工具；当“替换、组合、清理”成为问题时，再让 Cordis 接手。
