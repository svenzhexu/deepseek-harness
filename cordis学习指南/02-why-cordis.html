为什么需要 Cordis

一个框架能流行，通常不是因为它“功能多”，而是因为它让某类错误变得难以发生。 这一章我们把 Cordis 放回它诞生的场景：一个不断长大的应用、一群互不相识的插件、以及一个必须长期维护的团队。

难度 零基础 阅读 约 15 分钟 前置 第 1 章 关键词 耦合 · 生命周期 · 代价
本章你将学会
  • 用一个真实场景解释“为什么 main 会失控”；
  • 把六个常见痛点对应到 Cordis 的具体机制；
  • 说清 Cordis 的代价，而不是只背优点；
  • 用一张清单判断自己的项目是否值得引入 Cordis。

先承认一件事：main 函数很好

第 1 章那段二十行的待办程序，比任何框架都更值得作为起点。它没有隐藏的控制流，没有需要学习的生命周期， 出错时堆栈直接指向那一行代码。简单，本身就是一种竞争力。

所以“为什么需要 Cordis”这个问题，不能靠“因为 main 很烂”来回答。更准确的说法是： 当程序从“一个人写一次”变成“一群人改很多次”，main 所承担的角色会悄悄变化。 它从“执行步骤”变成了“系统的装配说明书”，而装配说明书是最不适合写死在代码里的东西。

一个小应用的长大过程

还是那个待办清单。我们把它按时间线拉长一点：

v1：一个文件，二十行

读写 JSON，增删改查。没有任何抽象，也不需要。此时引入 Cordis 是过度设计。

v2：加一个“统计”功能

你想知道每天新增了多少待办。main 里多了一行 const stats = new Stats(db)， 每次 add 之后调用 stats.record()。能跑，但“新增待办”这件事现在同时知道数据库和统计器。

v3：加一个 HTTP 接口

为了给手机用，你包了一层 HTTP。路由处理函数直接 import { db }，又直接 import { stats }。 依赖关系从“main 里的几行”扩散到了每个文件。

v4：允许第三方写扩展

有人想加“导出为 Markdown”，有人想加“到期提醒”。你不可能让每个扩展作者都来改你的 main.ts， 更不敢让他们直接碰你的数据库连接。你需要一种机制：让扩展自己声明需要什么，由宿主决定给不给、什么时候给。

v5：运行中改配置

用户想在设置页里把存储从本地文件切到 PostgreSQL，不重启进程。你发现：数据库连接是在 main 里创建的， 统计器持有它的引用，HTTP 路由缓存了它——要换，得把所有持有者一起拆掉再重建。而“所有持有者”是谁， 你已经数不清了。

走到这里，问题已经不是“代码写得不够漂亮”，而是系统缺少一套关于“能力、依赖、生命周期”的公共语言。 Cordis 提供的正是这套语言。

一句话

框架的价值，不在于让你少写代码，而在于让某一类错误变得难以发生。 Cordis 瞄准的那类错误是：依赖关系失控、启动顺序靠猜、资源清理靠自觉、替换实现靠改调用方。

六个反复出现的痛点

下面每一条都来自真实的工程现场，而不是教科书上的假设。每条后面，是 Cordis 给出的机制；先看思路，细节留到后面章节。

痛点 1 · 谁都被谁认识：编译期耦合

使用方直接 import 提供方的类，意味着“使用方”在编译时就绑定了“某一个实现”。 想换成测试用的内存版、云上的托管版，或者让第三方提供另一版，都得改使用方的代码。

Cordis 的答案：按名字寻址。 使用方只声明“我需要 db 这个服务”， 不关心它是文件、PostgreSQL 还是内存实现。提供方以 db 这个名字注册，双方在运行时通过 Context 相遇。

痛点 2 · 启动顺序靠人记

db 必须在 auth 前，migrate 必须在 auth 前， stats 又必须在 server 前。顺序写在注释里，靠 code review 维持；某天有人插入一行， 线上就多了一次空指针。

Cordis 的答案：依赖驱动加载。 插件声明 inject: ['db']，Cordis 就让它在 PENDING 状态等着；db 一出现，它自动进入 ACTIVE。顺序不再由文件位置决定， 而由依赖关系推导出来。

痛点 3 · 注册容易，撤销难

插件注册了一个定时器、一个文件监听、一个事件回调、一个工具。卸载时，你得逐一记得清理。 漏掉一个，就是内存泄漏或“卸载后还在跑”的幽灵行为；清理顺序错了，还会在关闭时抛异常。

Cordis 的答案：注册即副作用（Effect）。 所有通过 Cordis API 建立的注册都自动记在当前 Fiber 名下； 需要自己管理的资源，用 ctx.effect() 包起来并返回一个销毁函数。卸载时按规则统一撤销， 不需要“记得”。

痛点 4 · 换一个实现，牵动全身

测试环境想用假时钟，本地想用 SQLite，生产用 PostgreSQL，多租户还想让每个租户看到自己的数据库。 每换一次，就要改 import、改构造、改启动参数，甚至改业务代码。

Cordis 的答案：提供者与消费者分离，再加作用域隔离。 换实现只需要换“提供者”； isolate 可以让同一棵插件树里的两个分支看到不同的 db，互不影响。

痛点 5 · 配置散落在代码和文档里

端口、路径、开关、模型名、超时……有的在环境变量里，有的写死在常量里，有的只存在于 README。 改错一个，程序启动到一半才崩，错误信息还指向无关的地方。

Cordis 的答案：配置是插件契约的一部分。 插件声明一个 schema，Loader 在启动前校验； 配置来自 cordis.yml，可以分组、拆分、按环境覆盖。错误配置在加载时明确失败，而不是运行到一半才炸。

痛点 6 · 改一行代码要重启整个进程

调一个提示词、改一个工具描述，都要重启、重新登录、重新连数据库。对于长期运行的 agent 服务，这会让迭代速度慢得难以忍受。

Cordis 的答案：可逆的生命周期让热更新成为可能。 卸载旧插件 → 加载新插件， 只要每个插件都正确地释放了自己的 Effect，替换就是安全的。HMR 只是在这个能力上加了一个文件监听器。

痛点传统做法Cordis 机制你需要付出的
耦合 直接 import 实现 Service + inject 给能力起稳定名字
顺序 手写初始化序列 依赖驱动的 Fiber 状态机 接受“PENDING 是合法状态”
清理 手写 close / removeListener Effect + Fiber 统一撤销 每条注册都要有 disposer
替换 改 import / 改 main 换提供者 + isolate 理解作用域
配置 常量 + 环境变量 + 文档 Schema + Loader 维护 schema 与配置文件
演化 重启进程 可逆生命周期 + HMR 严格遵守 Effect 纪律

它借了哪些成熟思想

Cordis 并不发明新理论。它把几个已经被验证过的思想，组合成了一个具体可用的运行时：

控制反转与依赖注入 对象不自己创建依赖，而是由容器在合适的时机注入。Cordis 的注入不是构造函数参数，而是上下文属性。
微内核 内核只负责注册、解析、生命周期；所有具体能力都是插件。内核小，系统才能长得大。
发布 / 订阅 事件让“发出通知”和“处理通知”解耦。Cordis 在此之上加了顺序、并发、短路与中间件语义。
RAII 式资源管理 “获取资源”与“释放资源”绑定在同一个作用域里。Cordis 用 Effect 把这件事带到了 JavaScript。

包描述里称它为 Meta-Framework（元框架）：普通框架提供一组确定的 API，让你在里面填业务； 元框架提供的是“组合框架的框架”，具体有哪些能力、如何装配，由插件和配置决定。

官方目标

Cordis 把自己的目标概括为四件事：显式依赖注入、作用域服务、 生命周期管理的清理、可选的配置驱动加载。 它们正好对应前面六个痛点的解法——前三个是运行层，最后一个是装配层。

代价：Cordis 不是免费的

只讲优点的教程不值得信。引入 Cordis 会带来真实的成本，而且这些成本在项目早期尤其明显：

代价具体表现缓解方式
间接性 IDE 里不能从 ctx.db 直接跳到实现；要按服务名搜注册点。 统一命名规范；用声明合并补类型；维护服务目录。
隐式失败 依赖缺失时插件停在 PENDING，没有任何输出，看起来像“代码没生效”。 启动后检查 fiber 状态；把 PENDING 写进诊断日志。
调试跨度 调用栈会穿过 Context 代理和事件分发，比直接调用更长。 先定位“哪个插件”，再看具体函数；利用 fiber 名称。
学习曲线 Context、Fiber、Effect、waterfall 都要理解，才能写对。 先写小例子；本指南第 10 章用 80 行实现帮助建立直觉。
约定成本 服务要起名、事件要声明、每个注册都要有 disposer。 把规则固化成模板和 code review 检查项。
运行时开销 代理、Fiber、事件分发都有成本。对普通应用通常可忽略，但极热路径要留意。 热路径直接调用服务方法，不要每次走事件。
最常见的误用

把 Cordis 当成“更高级的 main”：所有插件仍然互相 import，只是外面套了一层 ctx.plugin。 这样既没有获得解耦，又增加了间接性，是双输。判断标准很简单： 删掉提供者的 import 后，消费者还能编译和运行吗？

一张清单：你的项目需要 Cordis 吗

不需要精确打分。如果下面有 三项以上为“是”，Cordis 很可能值得；如果只有一项，先别急。

问题为什么重要
会有第三方或多人分别写扩展吗？需要稳定的扩展点与依赖声明。
同一种能力有多个实现，需要按环境切换吗？服务寻址与隔离能省掉大量条件分支。
需要在运行中改配置或替换实现吗？可逆生命周期是热更新的前提。
资源多、清理容易漏吗？（连接、监听、定时器、子进程）Effect 能把“记得清理”变成默认行为。
需要多实例或多租户隔离吗？isolate 比手写命名空间更彻底。
这是一个长期运行、需要可观测的服务吗？Fiber 状态、插件目录、依赖关系都可用于诊断。

反过来说，这些情况通常不必用：

  • 代码少于几百行、只有你一个人维护的脚本；
  • 一次性数据处理、构建脚本、代码生成器；
  • 要被别人 import 的纯库——库不应该强迫调用方接受一个运行时；
  • 对启动时间和包体积极度敏感的 CLI；
  • 团队里没有人愿意维护这层抽象，且项目生命周期很短。

为什么这几年又火起来

Cordis 最早服务的是聊天机器人：大量第三方插件、需要热更新、需要按用户隔离、需要在不重启的情况下改配置。 Agent 运行时几乎是同一组需求的放大版：

  • 能力多：工具、文件系统、终端、浏览器、子智能体、模型提供方，每一项都可能被替换；
  • 参与者多：官方插件、实验插件、用户自带插件，不能都改主程序；
  • 生命周期长：会话持续数小时，配置和插件可能在运行中变化；
  • 策略复杂：审批、沙箱、预算、模型路由，需要在调用链上插入可组合的策略。

DeepSeek Harness 选择 Cordis 作为底座，本质上是在回答：“当 agent 的能力和策略都变成可插拔的零件时， 用什么来保证它们能安全地拼在一起？” 这也解释了为什么它的插件数量会如此之多，却仍然能保持相对清晰的结构。

本章小结

  • main 不是“错的”；它的问题在于把装配知识锁进了代码，难以替换和演化。
  • Cordis 用六种机制回应六个痛点：服务寻址、依赖驱动、Effect、隔离、配置校验、可逆生命周期。
  • 它组合了 IoC、微内核、发布订阅、RAII 等成熟思想，定位是“组合框架的元框架”。
  • 代价真实存在：间接性、PENDING 静默、学习曲线、约定成本；小项目要谨慎。
  • 判断标准不是“项目大不大”，而是“是否需要多方扩展、替换、热更新与长期维护”。

自测一下

用一句话说明：为什么“把所有东西放进 main”在项目变大后会失效？

因为依赖关系、启动顺序和清理责任都集中在一个文件里，只存在于作者脑中；每加一个功能，都要修改同一处， 并且无法在不影响其他模块的情况下替换实现。问题不在文件本身，而在知识没有分散到各自的模块里。

“依赖驱动加载”具体解决了什么问题？它又带来了什么新问题？

解决了手工编排顺序的问题：插件只要声明 inject，就会等到依赖就绪再启动。 新问题是：依赖永远缺失时，插件会安静地停在 PENDING，不报错也不输出，需要额外的诊断手段。

如果你只做一个 300 行的本地脚本，会用 Cordis 吗？为什么？

通常不会。没有第三方扩展、没有实现替换、没有长期运行的生命周期，引入框架只会增加阅读成本和启动开销。 但如果你预计它半年后会变成多人维护的插件化工具，提前建立服务边界也可能是合理的——关键是为未来的变化付费，而不是为框架而框架。
