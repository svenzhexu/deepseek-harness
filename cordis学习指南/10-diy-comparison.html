与手写 main 的异同

理解一个框架最快的方式，不是读它的文档，而是自己写一个“能跑的最小版本”，然后看它在哪里开始力不从心。 这一章我们用 80 行实现一个迷你插件容器，再把它和 Cordis 放在同一张桌子上逐项对照。

难度 进阶 阅读 约 30 分钟 前置 第 6–8 章 关键词 对照 · 取舍 · 迷你框架
本章你将学会
  • 亲手实现依赖注入 + 生命周期 + 事件的最小闭环；
  • 说清 Cordis 比“从 main 手写”多了哪些能力，分别值多少钱；
  • 判断什么时候迷你版本就够了，什么时候必须用成熟框架；
  • 理解框架复杂度的真正来源：边界条件，而不是 API 数量。

先明确：我们在比较三种东西

写法核心适合
A. 直接写 main 按顺序 new、调用、关闭。 小脚本、一次性任务、原型。
B. 手写迷你容器 自己实现注册、依赖、清理、事件。 学习；或需求极窄、不想引入依赖的项目。
C. Cordis 成熟的容器 + 生命周期 + 事件 + 加载器 + 生态。 插件平台、长期运行、多人扩展、需要热更新。

很多“框架之争”把 A 和 C 直接对比，结论往往是“小项目不需要框架”或“大项目必须用框架”。 真正有意思的对照是 B 和 C：它们做的是同一件事，只是完成度不同。

80 行迷你插件容器

下面这段代码实现了 Cordis 最核心的四件事：服务注册、依赖等待、Effect 清理、事件广播。 它不追求生产可用，只追求“看得懂、跑得通”。

mini-cordis.tsts
type Disposer = () => void | Promise<void>
type Plugin = ((ctx: Context) => void) & { inject?: string[] }

const pending = new Set<() => void>()

class Context {
  private services = new Map<string, any>()
  private disposers: Disposer[] = []
  private listeners = new Map<string, Function[]>()

  constructor(private parent?: Context) {}

  private find(name: string): Context | undefined {
    if (this.services.has(name)) return this
    return this.parent?.find(name)
  }

  has(name: string) {
    return !!this.find(name)
  }

  get(name: string): any {
    return this.find(name)?.services.get(name)
  }

  provide(name: string, value: any) {
    if (this.find(name)) throw new Error(`duplicate service: ${name}`)
    this.services.set(name, value)
    this.effect(() => () => { this.services.delete(name) })
    for (const retry of [...pending]) retry()
  }

  effect(setup: () => Disposer) {
    const dispose = setup()
    this.disposers.push(dispose)
    return dispose
  }

  on(event: string, listener: (...args: any[]) => void) {
    const list = this.listeners.get(event) ?? []
    list.push(listener)
    this.listeners.set(event, list)
    this.effect(() => () => {
      const index = list.indexOf(listener)
      if (index >= 0) list.splice(index, 1)
    })
  }

  emit(event: string, ...args: any[]) {
    for (const listener of this.listeners.get(event) ?? []) listener(...args)
  }

  plugin(plugin: Plugin) {
    const ctx = new Context(this)
    const start = () => {
      const missing = (plugin.inject ?? []).filter(name => !ctx.has(name))
      if (missing.length) {
        pending.add(start)
        return
      }
      pending.delete(start)
      plugin(ctx)
    }
    start()
    return {
      ctx,
      async dispose() {
        pending.delete(start)
        for (const dispose of ctx.disposers.splice(0).reverse()) await dispose()
      },
    }
  }
}

用起来是这样的：

demo.tsts
const root = new Context()
root.provide('db', { query: () => 'ok' })

root.plugin(Object.assign((ctx: Context) => {
  console.log('consumer sees', ctx.get('db').query())

  ctx.on('ping', () => console.log('pong'))
}, { inject: ['db'] }))

root.emit('ping')
终端output
consumer sees ok
pong

它已经具备了 Cordis 的骨架：

  • provide 把能力放进容器，inject 让插件等待依赖；
  • effect 收集清理函数，dispose 逆序执行；
  • on / emit 提供最小的事件广播；
  • 子上下文通过 parent 继承服务。

如果你能独立写出这段代码，说明你已经理解了 Cordis 80% 的核心思想。 剩下的 20%，才是它真正复杂、也真正值钱的地方。

迷你版本省略了什么

把上面的代码和 Cordis 对比，会发现差距不在“功能列表”，而在“边界条件”：

能力迷你版本Cordis
依赖缺失 记在一个全局 pending 集合里，服务一到就重试。 每个 Fiber 独立跟踪依赖快照；支持隔离作用域、提供者替换、可选依赖。
依赖消失 不处理；消费者继续持有旧引用。 自动卸载消费者，等提供者恢复后重载。
强依赖检查 只检查 inject 名字，不能阻止直接 ctx.db。 Proxy 拦截属性读取，没有 inject 直接报错。
卸载顺序 只处理当前上下文的 disposer。 Fiber 树递归卸载，父等子，异步清理可等待。
重入安全 卸载过程中再注册会直接漏掉。 处理“卸载时又注册”“卸载时又卸载”等竞态。
事件 同步遍历，无返回值、无优先级、无异步等待。 五种分发模式、waterfall 中间件、prepend/global、错误聚合。
配置 没有。 Schema 校验、默认值、配置更新、volatile 引用。
隔离 没有。 isolate、intercept、Loader 级作用域。
装配 代码里手动 plugin。 Loader + cordis.yml，支持分组、禁用、补丁。
热更新 没有。 HMR 监听文件，卸载/重载受影响的 Entry。
诊断 console.log。 Fiber 状态、Effect 树、注册表枚举、错误堆栈拼接。
类型 any 为主。 声明合并让服务名、事件名、配置都有类型。
关键洞察

这 80 行代码的“核心逻辑”只占 Cordis 源码的一小部分；其余大部分代码在处理 失败、并发、重入、隔离和错误信息。框架的复杂度不是凭空来的， 它只是把你在生产环境迟早要写的边界处理，提前写好了。

同一个需求，两种写法

假设应用由三部分组成：数据库、统计、命令行。统计依赖数据库，命令行依赖两者。 下面是传统 main 与 Cordis 的对照：

传统 main.tsts
const db = await openDatabase(config.dbUrl)
const stats = new Stats(db)
const cli = new Cli(db, stats)

await cli.start()
console.log('app ready')

process.on('SIGINT', async () => {
  await cli.stop()
  await stats.flush()
  await db.close()
  process.exit(0)
})
Cordis main.tsts
const ctx = new Context()

await ctx.plugin(Database, config)
await ctx.plugin(Stats)
await ctx.plugin(Cli)

console.log('app ready')

process.on('SIGINT', async () => {
  await ctx.fiber.dispose()
  process.exit(0)
})

表面上看，Cordis 版本甚至更短。真正的差别在“看不见的地方”：

问题传统版本Cordis 版本
数据库连接失败 openDatabase 抛错，后面的代码不执行；需要自己保证清理。 插件 FAILED，await ctx.plugin() 抛错；已注册的 Effect 会回卷。
统计初始化慢 阻塞 main；或者手动改成并行并处理竞态。 Fiber 并行启动，依赖方等它就绪；不需要手写 Promise 编排。
换一个数据库实现 改 import、改构造、改类型。 换提供者插件；消费者不变。
测试时用假数据库 改 main 或引入依赖注入框架。 在子上下文里挂一个测试提供者。
运行中重载统计插件 几乎不可能，除非你自己实现卸载。 fiber.dispose() + 重新 plugin；HMR 自动做。
关闭顺序 手写，且容易漏。 Fiber 树 + Effect 逆序，自动处理。

注意：Cordis 并没有让“数据库连接”这件事本身变简单。它让连接与其他部分的关系变简单。 业务逻辑仍然要你自己写，错误仍然要你自己处理。

另一种“自己实现”：业务服务本身

如果你说的“服务”不是指框架，而是指一个具体业务能力（存储、通知、计费），那么两种写法的业务代码几乎一样， 区别只在“谁来创建、谁来注入、谁来关闭”。

手写：服务由 main 创建和关闭ts
const db = await openDatabase(config.dbUrl)
const todos = new TodoStore(db)
await todos.init()

// ... 把 todos 传给需要它的模块

await todos.close()
await db.close()
Cordis：服务由插件注册，生命周期归 Fiberts
class TodoStore extends Service {
  constructor(ctx: Context, config: Config) {
    super(ctx, 'todoStore')
  }

  async [Service.init]() {
    // ... 建立连接
    return () => this.close()
  }
}

export function apply(ctx: Context, config: Config) {
  ctx.plugin(TodoStore, config)
}
维度手写业务服务Cordis 服务
业务方法完全一样完全一样
谁创建main提供者插件
谁找到它手动传参 / import 单例按服务名 inject
谁关闭main 里的 close 调用Effect / Service.init 返回的 disposer
换实现改 main 与调用方换提供者
多实例自己传不同参数isolate

所以“自己实现服务”与“用 Cordis 实现服务”并不冲突：业务逻辑可以原样保留， 你只是把“创建、寻址、关闭”这三件事交给了框架。第 11 章的 TodoStore 就是这种写法。

代价对照

第 2 章列过 Cordis 的成本。放在与手写版本的对照里，这些成本更具体：

  • 代码量：Cordis 核心加上 loader 等包，远大于 80 行；但你的业务代码可能更少，因为编排和清理被移走了。
  • 启动时间：代理、依赖解析、模块导入都有开销。对 CLI 来说可能感知明显；对长期运行的服务通常可忽略。
  • 调试：直接调用栈最容易读；Cordis 的栈会穿过代理和事件分发。熟悉 Fiber 名称后会好很多。
  • 可预测性：手写版本的执行顺序一目了然；Cordis 的顺序由依赖决定，需要工具辅助观察。
  • 团队成本：每个新人都要学 Context、Fiber、Effect；小团队短期项目可能不划算。
不要为了“架构感”引入框架

如果你现在只有一个 main、三个模块、没有第三方扩展、也不打算热更新，那么手写版本不仅够用， 而且更容易维护。等到“换实现要改很多文件”“卸载总是漏东西”“配置开始分散”时，再引入 Cordis， 迁移成本反而更低——因为那时你已经知道它要解决什么。

自己实现一遍，能学到什么

依赖解析不是魔法 它就是“查找 + 等待 + 通知”三件事。理解这一点，PENDING 就不再神秘。
生命周期就是所有权 谁创建、谁销毁、销毁时通知谁。Fiber 只是把这三件事显式化了。
清理比创建难 创建只有一条路径，清理要考虑异常、顺序、重复调用、异步未完成。
复杂度藏在边界 热更新时旧实例还在跑、卸载时又注册、提供者中途消失——这些才是框架的真正工作。

决策清单

你的情况建议
学习 Cordis / 想理解插件系统 先写一遍迷你版本，再读第 4–8 章。
一次性脚本、构建工具、代码生成 直接 main，不要引入框架。
要发布给别人用的库 暴露普通函数/类；不要强迫调用方接受 Cordis。
多人维护、需要第三方扩展 Cordis 值得；先从小范围插件开始。
需要运行中换实现、热更新 Cordis 几乎是必需；迷你版本很难补齐这些边界。
团队完全没经验、项目只有两周 先用 main；把服务边界设计好，未来再迁移。

本章小结

  • 迷你版本证明了 Cordis 的核心思想并不复杂：注册、等待、通知、清理、广播。
  • Cordis 的额外价值主要在边界条件：依赖消失、重入、异步清理、隔离、错误诊断。
  • 传统 main 与 Cordis 的差别不在代码长度，而在“关系”由谁维护。
  • 框架有真实成本：启动、调试、学习、团队约定；小项目要谨慎。
  • 最好的学习路径：先手写 80 行，再用 Cordis 重写同一个程序，对照差异。

自测一下

迷你版本的 pending 集合与 Cordis 的 Fiber 依赖跟踪，最本质的差别是什么？

迷你版本只有一个全局待办集合，谁缺依赖都往里塞，服务一到就全部重试；它不记录“某个插件依赖某个服务的哪个作用域版本”。 Cordis 为每个 Fiber 保存依赖快照（服务名 + 提供者 Fiber），因此能精确处理隔离、替换、提供者消失与重入。

为什么说“框架的复杂度主要来自边界条件”？举两个例子。

例如：插件在异步初始化尚未完成时被卸载，框架要等初始化结束再清理；插件在卸载过程中又注册了新的 Effect， 框架要拒绝或正确纳入本次卸载。这些情况在正常路径上永远不会遇到，但在热更新和故障恢复时必然出现。

如果一个项目只有 300 行、没有第三方扩展，你会建议用 Cordis 吗？

通常不会。这个规模下，main 的直白和低启动成本更有价值。可以先把“能力边界”设计好（例如用接口隔离数据库）， 等出现替换、扩展、热更新需求时再迁移，成本并不高。
