Context：能力面板

在 Cordis 的代码里，ctx 几乎无处不在。它看起来只是一个参数，实际却同时扮演三个角色： 服务的容器、插件的作用域、生命周期的归属。这一章我们把 ctx 拆开，看看它到底是怎么找到 ctx.db 的。

难度 入门 阅读 约 20 分钟 前置 第 3 章 关键词 服务解析 · 隔离 · 作用域
本章你将学会
  • 解释 ctx.foo 与 ctx.get('foo') 的区别；
  • 用 provide 注册服务，并理解为什么它能自动撤销；
  • 用 isolate 让两个分支看到不同的实现；
  • 避开“用错上下文注册”这个最常见的泄漏来源。

ctx 不是普通对象

第一次看到 ctx.db，很容易以为 db 是某个对象上的普通属性。其实不是。 Cordis 给每个上下文套了一个 Proxy：当你读取一个属性时，代理会去服务仓库里按名字查找实现。

这带来两个直接结果：

  • 按名字寻址：你不需要知道 db 是哪个类的实例，也不需要 import 它。
  • 运行时检查依赖：在插件上下文里，读取一个不在祖先链上的服务却没用 inject，Cordis 会直接报错，而不是返回 undefined 让你在更远的地方崩掉。
类比 · 配电箱与房间

根上下文是整栋楼的配电箱；每个插件拿到的是自己房间的“分电箱”。房间里的插座名字（db、logger） 和楼里一致，但某个房间可以单独接一条线路（隔离），不影响其他房间。

读取：get 与属性访问

先看一个完整的对比例子。它注册一个 greeting 服务，然后分别在“没有 inject”和“有 inject”的插件里读取它。

read.tsts
import { Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    greeting: string
  }
}

const root = new Context()

const provider = root.plugin(function greetingProvider(ctx) {
  ctx.provide('greeting', 'hello')
})

const withoutInject = (ctx: Context) => {
  console.log('get:', ctx.get('greeting'))

  try {
    console.log('property:', ctx.greeting)
  } catch (error) {
    console.log('error:', (error as Error).message)
  }
}

await provider
await root.plugin(withoutInject)
终端output
get: hello
error: cannot get property "greeting" without inject

同一个服务，两种读法，行为不同。这里的 greeting 由兄弟插件提供， 不在消费者的祖先链上，所以属性读取会失败：

写法是否要求 inject找不到时适用场景
ctx.greeting 当提供者不在祖先链上时 沿父链到根仍找不到，抛出异常并提示缺少 inject 强依赖；插件没有它就活不了。
ctx.get('greeting') 否 返回 undefined 可选依赖；没有也能降级运行。
ctx.get('greeting', false) 否 即使提供者未激活也能拿到值 诊断、调试；普通业务不要用。

加上 inject 之后，属性读取就合法了，而且类型也更自然：

read-injected.tsts
import { Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    greeting: string
  }
}

const root = new Context()
const provider = root.plugin(function greetingProvider(ctx) {
  ctx.provide('greeting', 'hello')
})

const plugin = Object.assign((ctx: Context) => {
  console.log(ctx.greeting)
}, { inject: ['greeting'] })

await provider
await root.plugin(plugin)
终端output
hello
属性访问会沿父链查找

在根上下文或祖先插件里提供的服务，子插件即使没写 inject 也能读到——它们就在父链上。 真正触发“without inject”报错的，是兄弟分支或其他子树提供的服务：它们不在父链上， Cordis 不会去全局仓库里“捞”，而是要求你用 inject 明确声明。 ctx.get 则是显式的全局查找，不受父链限制。

写入：provide、set 与 Service

服务是怎么进入上下文的？最底层的方法是 ctx.provide(name, value)：

provide.tsts
import { Context } from '@deepseek-ai/cordis'

const root = new Context()
const dispose = root.provide('clock', {
  now: () => Date.now(),
})

console.log(root.get('clock').now() > 0)

dispose()
console.log(root.get('clock'))
终端output
true
undefined

provide 返回一个销毁函数。它被注册为当前 Fiber 的一个 Effect，所以即使你不手动调用， 插件卸载时它也会执行。手动调用则让服务立刻下线，等待它的插件会收到通知。

API用途注意
ctx.provide(name, value) 注册一个服务值 同一作用域内不能重复注册同名服务。
ctx.set(name, value) 更新自己提供的服务值 只有提供这个服务的 Fiber 才能改。
class X extends Service 以类的方式提供服务 推荐用于真正的“能力”，见第 6 章。
ctx.accessor(name, options) 定义一个计算属性 适合派生值，不适合有状态的服务。
ctx.mixin(source, keys) 把服务的成员转发到 ctx 上 框架内部大量使用；普通插件少用。

provide 与 Service 怎么选

provide 是底层原语，适合极小的值或测试替身；Service 是它的“带类型、可继承、可配置”的封装。 如果你要提供的能力有方法、有状态、可能需要被替换，用 Service；如果只是一个常量或简单对象， provide 就够了。两者在运行时的归宿相同：都进入 Reflect 的服务仓库，都随 Fiber 卸载。

上下文是一棵树

每次 ctx.plugin()，Cordis 都会基于当前上下文创建一个子上下文，并把它和新建的 Fiber 绑定。 子上下文通过原型链继承父上下文的所有能力，同时拥有自己的服务作用域和生命周期归属。

tree.tsts
import { Context } from '@deepseek-ai/cordis'

const root = new Context()

const parent = root.plugin(function parentPlugin(ctx) {
  ctx.provide('name', 'parent')
  console.log('parent sees:', ctx.get('name'))

  ctx.plugin(function childPlugin(ctx) {
    console.log('child sees:', ctx.get('name'))
    console.log('same root:', ctx.root === root)
  })
})

await parent
await parent.dispose()
终端output
parent sees: parent
child sees: parent
same root: true

子上下文能看到父上下文提供的服务；父上下文看不到子上下文新增的服务。这与 JavaScript 的原型链一致： 查找从当前节点开始，逐级向上，直到根。ctx.root 始终指向同一个根上下文。

易错 · 用错上下文注册

在插件里，如果你把外层的 root 传进回调，并用 root.on(...) 注册监听器， 这个监听器会记在根 Fiber名下，而不是当前插件。插件卸载时，它不会被清理。 规则很简单：在哪个上下文里注册，就归哪个 Fiber 管。插件内部请始终使用参数传入的 ctx。

隔离：同一棵树，不同的世界

假设你要在一个进程里跑两个租户，各自有独立的数据库连接。直接共享一个 db 服务显然不行； 为每个租户改一套服务名又会污染全局命名空间。isolate 解决的正是这个问题。

isolate.tsts
import { Context } from '@deepseek-ai/cordis'

const root = new Context()
root.provide('db', 'main-db')

const tenantA = root.isolate('db')
const tenantB = root.isolate('db')

tenantA.provide('db', 'tenant-a-db')
tenantB.provide('db', 'tenant-b-db')

console.log('root    :', root.get('db'))
console.log('tenant A:', tenantA.get('db'))
console.log('tenant B:', tenantB.get('db'))
终端output
root    : main-db
tenant A: tenant-a-db
tenant B: tenant-b-db
root：db = main-db
tenantAdb = tenant-a-db
独立作用域
tenantBdb = tenant-b-db
独立作用域

isolate(name) 每次调用都会创建一个新的作用域标签。如果你希望两个上下文共享同一个隔离域， 可以显式传入同一个标签：

shared-scope.tsts
const scope = Symbol('team-a')

const a1 = root.isolate('db', scope)
const a2 = root.isolate('db', scope)

a1.provide('db', 'shared-db')
console.log(a2.get('db')) // shared-db

这正是 Loader 的 isolate 配置项背后的机制：isolate: { db: true } 为单个条目创建独立域； isolate: { db: 'team-a' } 则让多个条目共享同一个命名域。第 9 章会看到具体写法。

intercept：只改配置，不换实现

有些服务支持“局部配置覆盖”，例如日志级别、默认模型、超时时间。它们不是换一个实现，而是让同一实现在不同分支里 读到不同的配置。ctx.intercept(name, config) 就是为此准备的：

intercept.tsts
const quiet = root.intercept('logger', { level: 0 })
const verbose = root.intercept('logger', { level: 3 })

quiet.plugin((ctx) => {
  ctx.logger.info('这条不会显示')
})

verbose.plugin((ctx) => {
  ctx.logger.info('这条会显示')
})

intercept 只对声明了 [Service.config] 的服务生效，而且如何合并由服务自己决定。 不用太早深入它：先记住“isolation 换实现，intercept 改配置”这个区分就够了。 上面的输出来自 logger-console 导出器；没有它，日志只会进入内存缓冲区。

四个常见错误

错误后果正确做法
在插件里用外层 root 注册 注册归根 Fiber，插件卸载后仍然存活 始终使用回调参数里的 ctx
把 ctx 存到模块级变量 热更新后仍指向旧 Fiber，读到已释放的服务 在插件函数内部使用；需要跨调用保存时存服务，不存 ctx
忘了 inject 就用 ctx.foo 插件直接 FAILED，或读到错误的作用域 强依赖写进 inject；可选依赖用 ctx.get
重复 provide 同名服务 后注册者报错：“service has been registered” 先确认没有提供者；需要多实例就用 isolate
一个判断技巧

当你写下 ctx.xxx 时，问自己两个问题：这个服务是谁提供的？ 我声明依赖了吗？ 如果答不上来，先用 ctx.get('xxx') 打印一下， 或者去注册表里搜 provide('xxx') / super(ctx, 'xxx')。

本章小结

  • ctx 是代理：属性读取会按名字解析服务，并对不在祖先链上的服务强制 inject。
  • ctx.get 用于可选依赖，找不到返回 undefined；属性访问用于强依赖。
  • provide 注册服务并返回销毁函数；Service 是它更高层的封装。
  • 上下文是一棵树：子能看到父，父看不到子；注册归当前 Fiber 所有。
  • isolate 换实现，intercept 改配置；两者都只影响子分支。

自测一下

为什么插件里 ctx.greeting 会报错，而 ctx.get('greeting') 不会？

属性访问被视为强依赖：Cordis 要求插件先通过 inject 声明，才会在 Fiber 上建立依赖快照。 get 是显式的可选取值，不要求 inject，因此找不到时返回 undefined。

两个租户需要不同的 db，应该用 intercept 还是 isolate？

用 isolate。它隔离的是服务实现的查找作用域，让两个分支各自解析到不同的提供者。 intercept 只改变同一实现的配置，不改变“谁来提供”。

在插件回调里把外层 root 传给 setTimeout，然后用 root.on 注册监听器，会有什么问题？

监听器会注册到根 Fiber 上，插件卸载时不会被移除，造成泄漏或“卸载后还在响应”。 应改为使用回调参数 ctx，并确保异步回调捕获的是这个 ctx。
