什么是 Cordis

Cordis 不是“又一个 Web 框架”，而是一种组织程序的方式：把“我来创建、我来调用、我来清理”， 换成“我声明需要什么、我提供什么、用完请撤销”。这一章我们先不背概念，只从一段普通的 main 函数出发，看看这种换法到底换掉了什么。

难度 零基础 阅读 约 15 分钟 前置 会一点 JavaScript 关键词 插件 · 上下文 · 生命周期
本章你将学会
  • 说出 Cordis 与“把所有东西写在 main 里”的根本区别；
  • 读懂一个最小可运行的 Cordis 程序；
  • 用六个关键词描述 Cordis 的组成；
  • 判断 Cordis 不是什么，避免用错场景。
一句话定义

Cordis 是一个用 TypeScript 编写的插件框架：它把应用拆成可挂载的插件， 用 Context 管理服务，用 Fiber 管理每个插件的生命周期， 用 Event 让插件之间不必互相认识。

先看一段没有 Cordis 的程序

假设你要写一个极简的待办清单。最自然的写法，是建一个 main.ts，从头到尾把事做完：

main.tsts
import { readFile, writeFile } from 'node:fs/promises'

const FILE = './todos.json'
const todos = JSON.parse(await readFile(FILE, 'utf8').catch(() => '[]'))

async function add(title: string) {
  todos.push({ title, done: false })
  await writeFile(FILE, JSON.stringify(todos, null, 2))
  console.log(`added: ${title}`)
}

const command = process.argv[2]
if (command === 'add') {
  await add(process.argv[3] ?? 'untitled')
} else {
  console.log(todos)
}

运行它，输出完全符合预期：

终端output
$ node --import tsx main.ts add "买牛奶"
added: 买牛奶

这段代码没有问题。它直白、好读、好调试，二十行就能跑。任何一上来就告诉你“这样写不对”的框架， 都值得警惕。

Cordis 要解决的不是这二十行，而是它之后的事。

当需求长大，main 开始变形

产品经理来了。你要加：可切换的存储（本地文件 / 数据库）、操作统计、一个 HTTP 接口、按用户隔离数据、 运行中改配置不重启、以及让第三方写扩展。半年后，main.ts 可能长成这样：

main.ts（示意，已经很难维护）ts
import { openDatabase } from './db.ts'
import { Auth } from './auth.ts'
import { Stats } from './stats.ts'
import { createServer } from './server.ts'
import { loadConfig } from './config.ts'
import { migrate } from './migrate.ts'

const config = await loadConfig()
const db = await openDatabase(config.dbUrl)
await migrate(db)
const auth = new Auth(db, config.secret)
const stats = new Stats(db)
const server = createServer({ db, auth, stats })
await server.listen(config.port)
stats.attach(server)

process.on('SIGINT', async () => {
  await server.close()
  await stats.flush()
  await db.close()
})

它仍然能跑，但每次加功能，你都要在同一个文件里做四类决定：

你被迫做的决定典型症状
创建谁 所有模块都要在 main 里 new 一遍；想换数据库，得改 main。
按什么顺序创建 db 必须在 auth 前，migrate 必须在 auth 前；顺序靠注释和记忆维持。
什么时候清理 退出时要记得关 server、flush stats、关 db；漏一个就泄漏，顺序错了就报错。
怎么替换 测试想用内存数据库，只能改 import；第三方想扩展，只能改 main 的源码。

注意：这不是 main 的错，也不是“函数写多了”的错。真正的问题是—— 所有关于“谁依赖谁、谁先启动、谁负责收尾”的知识，都集中在一个文件里，而且只存在于你的脑子里。

类比 · 从自己拉电线到配电箱

小房子里，你可以自己从电表拉一根线到灯泡。房子变大、房间变多以后，继续这么干就会变成一团乱麻。 更合理的做法是装一个配电箱：每个房间只说“我需要一个插座”，电工按标准把线接好；要换线路，也不必把墙砸开。 Cordis 的 Context，就是软件世界的配电箱。

换一种问法：从“我来做”到“我声明”

与其让 main 依次命令每个模块，不如让每个模块自己说清楚两件事： 我需要什么，以及我能提供什么。剩下的编排工作，交给框架。

传统写法Cordis 的写法
我在 main 里 new Database() 我声明：我需要一个叫 db 的服务
我手动保证 db 先于 auth 初始化 我说：没有 db 就別启动我；有了再叫我
退出时我记得调用 db.close() 我注册时交出一个“撤销函数”，卸载时框架替我调用
换实现就改 import 和 new 换掉提供者即可，使用方一行不用改
要测试就 mock 整个 main 在子上下文里换一个测试用提供者

这种“把控制权交给框架、自己只做声明”的思路，在软件工程里叫 控制反转（Inversion of Control，IoC）。Cordis 把它具体化成了几个可以操作的部件： 上下文、插件、Fiber、服务、事件、Effect。

最小可运行的 Cordis 程序

先别管上面那些名词。下面是一个完整、可运行的 Cordis 程序，只有十几行：

hello.tsts
import { Context } from '@deepseek-ai/cordis'

const ctx = new Context()

const fiber = ctx.plugin((ctx) => {
  console.log('hello from a plugin')

  ctx.effect(() => {
    console.log('plugin loaded')
    return () => console.log('plugin disposed')
  })
})

await fiber
await fiber.dispose()
终端output
$ node --import tsx hello.ts
hello from a plugin
plugin loaded
plugin disposed

代码里的 @deepseek-ai/cordis 是本仓库 vendor 后的包名；上游写作 cordis， API 完全相同。后文统一使用本仓库的包名，遇到网上文章时替换即可。

逐行拆开看：

  • new Context() 创建根上下文。它是整个应用的容器，内置了日志、事件、插件注册表等基础服务。
  • ctx.plugin(fn) 把一个函数挂载为插件。Cordis 会调用这个函数，并把一个属于该插件的子上下文传进去。
  • ctx.effect(...) 登记一件“可以被撤销的事”。函数体立刻执行；它返回的函数，会在插件卸载时执行。
  • await fiber 等这次挂载稳定（没有正在进行的初始化）。注意：缺依赖时插件会停在 PENDING，await 也会立即返回，并不代表已经 ACTIVE。
  • await fiber.dispose() 卸载插件：先执行 Effect 的清理函数，再释放它注册过的所有东西。
注意 · 这不是普通的回调

你可能会说：“ctx.plugin(fn) 不就是传个回调吗？”表面上是，区别在于所有权： 这个回调里通过 ctx 注册的监听器、服务、定时器，全部记在返回的 fiber 名下。 fiber 一卸载，它们自动撤销。普通回调没有这层归属关系，清理得靠你自己。

如果你不熟悉这些 TypeScript 语法

示例里会出现三种“看起来像 JavaScript、但又不是”的写法，先认识一下即可：

  • 类型注解：ctx: Context 只是告诉编辑器“ctx 是 Context 类型”，运行时会被完全擦除，不会多出任何代码。
  • import type：只导入类型，编译后整行消失。因此一个文件可以“只依赖类型”而不产生运行时依赖。
  • 声明合并：declare module '@deepseek-ai/cordis' { ... } 往已有接口里追加字段，让 ctx.myService 获得类型。它不生成运行时代码。

六个关键词，先混个脸熟

后面的章节会逐一展开。现在只需要建立一个大概的印象——它们分别在回答不同的问题：

关键词它回答的问题生活类比代码里长什么样
Context
上下文		 “能力放在哪里？” 配电箱：每个插座有名字 ctx.tools、ctx.get('db')
Plugin
插件		 “一段功能怎么装进去？” 可插拔的模块 ctx.plugin(fn) 或 Service 子类
Fiber
纤程 / 运行实例		 “这次挂载归谁管？什么时候卸载？” 插头 + 租约 const fiber = ctx.plugin(...)
Service
服务		 “一项能力怎么被别处使用？” 带名字的插座 ctx.tools.register(...)
Event
事件		 “发生了某事，怎么通知所有关心的人？” 广播 ctx.emit('todo/added', todo)
Effect
副作用 / 可撤销注册		 “注册了东西，怎么保证收得回来？” 登记表 + 反注册 ctx.effect(() => () => cleanup())

这六个词不是六个孤立的功能，而是一条链： 插件挂载后得到一个 Fiber；插件通过 Context 提供或获取 Service， 用 Event 广播消息；所有注册都作为 Effect 记在 Fiber 名下，卸载时统一撤销。

Cordis 不是什么

把边界说清楚，比堆定义更有用：

  • 不是 Web 框架。 它不带路由、HTTP 解析、模板引擎。你可以用 Cordis 组织一个 Web 应用，但 Web 能力来自别的插件。
  • 不是打包器或编译器。 它不处理 .ts 到 .js 的转换；示例里的 tsx 是另一个工具。
  • 不是“必须用 TypeScript”。 运行时是普通 JavaScript；TypeScript 只是让服务名和事件名在编译期可检查。
  • 不是 DeepSeek Harness 专属。 Harness 只是它最大的使用者之一；Koishi 等项目也使用同一套架构。
  • 不是银弹。 十几行的一次性脚本、纯算法库、对启动体积极度敏感的 CLI，用 Cordis 往往得不偿失。第 10 章会认真讨论代价。

它从哪里来

Cordis 由 Shigma 开发，长期作为开源聊天机器人框架 Koishi 的底层架构。 Koishi 于 2020 年发布第一个正式版本，插件市场里有上千个插件；这种“大量第三方插件 + 可热插拔”的需求， 正是 Cordis 的设计土壤。

DeepSeek Harness 把 Cordis 4.x vendor（复制进自己的仓库，而不是从 npm 安装）作为整个 agent runtime 的地基：工具、模型适配器、文件访问，甚至 agent loop 本身，都是挂在这个框架上的插件。 这也是为什么你在本仓库里看到的是 @deepseek-ai/cordis，而不是 cordis。

本章小结

  • Cordis 是插件框架，不是 Web 框架；它管理的是“能力如何组合与拆除”，不是业务逻辑。
  • 它把 main 里的“创建、排序、清理、替换”换成了声明依赖 + 注册 Effect + 按名字寻址。
  • 一次 ctx.plugin() 产生一个 Fiber；插件注册的一切都归这个 Fiber 所有。
  • Context 是能力容器，Service 是具名能力，Event 是广播，Effect 是可撤销注册。
  • 小脚本不必用 Cordis；它的价值随“插件数量、替换需求、生命周期复杂度”增长。

自测一下

Cordis 帮你管理的核心东西是什么？是业务逻辑吗？

不是业务逻辑，而是能力之间的依赖关系与生命周期：谁需要谁、什么时候启动、注册了什么、什么时候撤销。 业务仍然由你的插件实现。

ctx.plugin(fn) 返回的 Fiber 有什么用？为什么不能忽略它？

Fiber 是这次挂载的运行实例句柄，记录状态、依赖、配置和所有 Effect。你可以 await 它来等待挂载稳定 （缺依赖时会停在 PENDING，await 会立即返回），调用 dispose() 来卸载。忽略它不会立刻出错， 但你会失去“精确控制这一次挂载”的能力；对于长期运行的应用，卸载和重启都依赖它。

下面哪些场景不太值得引入 Cordis？
A. 十行的一次性数据清洗脚本；B. 需要第三方扩展的桌面应用；C. 一个纯数学工具库；D. 需要热更新插件的大型服务。

A 和 C。一次性脚本没有“组合与拆除”的复杂度；纯库应该只暴露函数，不应该强迫调用方接受一个运行时。 B 和 D 正是 Cordis 的典型场景：多方扩展、实现替换、生命周期管理。
