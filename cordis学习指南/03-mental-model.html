一张图看懂 Cordis

前面两章回答了“是什么”和“为什么”。这一章给你一张地图：Cordis 由哪几层组成、一次插件加载到底发生了什么、 哪些包属于核心、哪些只是外围工具。后面每一章，都是在这张地图上放大一个区域。

难度 零基础 阅读 约 20 分钟 前置 第 1–2 章 关键词 架构 · 时序 · 包边界
本章你将学会
  • 画出 Cordis 的三层结构，并说清每层的职责；
  • 列出六个核心部件，知道它们各自解决什么问题；
  • 按顺序复述一次插件加载的完整过程；
  • 区分 Cordis 核心、官方插件与 DeepSeek Harness 插件。

三层结构：组合、加载、运行

把 Cordis 想象成一座工厂。最上面是订单（要生产什么），中间是调度（把原料送进车间）， 下面是车间（真正干活）。三层可以独立替换：你可以不用 Loader，直接在代码里下订单；也可以不用插件， 只把 Context 当一个服务容器。

组合
main.ts 或 cordis.yml 决定装哪些插件、给什么配置、是否禁用、如何分组。它不实现能力，只做装配。
↓
加载
Loader · Include · Group 读取配置文件、导入模块、维护 Entry 树、把配置变化同步到运行中的插件。可选。
↓
运行
Context + Fiber + 核心服务 服务存取、依赖解析、事件分发、生命周期与清理。Cordis 真正不可替代的部分。
Registry插件注册表：把函数/类/对象统一成可执行插件。
Reflect服务仓库 + 代理拦截：让 ctx.xxx 按名字解析。
Events事件总线：emit / waterfall / parallel / serial / bail。
Fiber每次挂载的生命周期、依赖状态与 Effect 归属。
↕
插件
你的插件 A / B / C … 每个插件对应一个 Fiber，通过 provide 提供能力、通过 inject 声明依赖、通过 on 监听事件、通过 effect 管理资源。
先记住这个比例

你 90% 的时间只会和运行层打交道：写插件、用服务、发事件、注册 Effect。 Loader 和配置文件是“应用已经成型之后”的便利工具，不是理解 Cordis 的前提。

六个核心部件

Cordis 的根上下文在创建时，会安装几个内置服务，并给每个上下文挂上 Fiber 句柄。它们不是“业务服务”， 而是框架自己的基础设施。你可以通过 ctx.registry、ctx.events 这样直接访问， 也可以使用混入到 ctx 上的快捷方法。

部件访问方式职责你什么时候会用到
Registry ctx.registry
ctx.plugin()		 登记插件运行时、创建 Fiber、按插件回调去重。 挂载子插件、检查某个插件是否已加载。
Fiber ctx.fiber 当前插件实例的状态、依赖快照、配置与清理列表。 诊断状态、手动 dispose、读取当前插件名。
Reflect ctx.reflect
ctx.get / provide		 服务仓库、属性声明、代理读写、隔离作用域解析。 提供服务、可选取服务、定义访问器。
Events ctx.events
ctx.on / emit		 类型化事件、五种分发模式、监听器生命周期。 广播通知、拦截决策、观察框架状态。
Service 继承 Service 把“一个对象”注册为具名服务，并随 Fiber 卸载。 提供一项可被其他插件调用的能力。
Logger ctx.logger 结构化日志、命名日志器、导出器管理。 输出诊断信息；默认只缓冲，需要导出器才显示。
进阶 · 为什么是“代理”

ctx 不是普通对象，而是一个 Proxy。当你写 ctx.db 时，代理会去服务仓库里找 db 的实现；找不到就抛错，并提示你“是不是忘了 inject”。这也是 Cordis 能在运行时对跨分支的服务强制依赖声明的原因。 第 4 章会详细拆开它。

插件树：Fiber 的父子关系

插件不是平铺的列表，而是一棵树。每个插件拿到的是子上下文，在它里面挂载的插件又是它的子节点。 父节点卸载时，整棵子树会一起卸载；dispose() 会等子树也清理完才结束。

tree.tsts
import { Context } from '@deepseek-ai/cordis'

const root = new Context()

const parent = root.plugin(function parentPlugin(ctx) {
  console.log('parent: loaded')

  ctx.plugin(function childPlugin(ctx) {
    console.log('child: loaded')
    ctx.effect(() => () => console.log('child: disposed'))
  })

  ctx.effect(() => () => console.log('parent: disposed'))
})

await parent
await parent.dispose()
终端output
parent: loaded
child: loaded
parent: disposed
child: disposed

这里父清理先打印，是因为它比“子插件”更晚注册，而 Effect 按注册逆序撤销。 不要把父子顺序当成固定保证：能保证的是，parent.dispose() 返回时， 整棵子树都已经卸载完毕。如果某两步必须按特定顺序执行，把它们放进同一个 disposer 里显式 await。

一次加载的完整时序

这是全书最重要的一张时序图。你不需要一次记住所有细节，但要知道每一步在做什么，尤其是 PENDING 是怎么来的、ACTIVE 是什么时候发生的。

1
创建根 Context安装 Registry、Reflect、Events、Logger；根 Fiber 直接是 ACTIVE。
↓
2
ctx.plugin(plugin, config)Registry 把函数 / 类 / { apply } 统一成一个可执行回调，并找到（或创建）它的运行时记录。
↓
3
创建 Fiber（PENDING）Fiber 记录原始配置、解析后的 inject、父上下文；此时还没有执行任何插件代码。
↓
4
检查依赖对 inject 里的每个服务名，在 Reflect 仓库中查找实现；缺一个就停在 PENDING，等通知。
↓
5
进入 LOADING，解析配置先走 internal/config 瀑布，再用插件声明的 schema 校验配置；不合法直接 FAILED。
↓
6
执行插件函数插件被直接调用；类插件被 new；对象插件调用 apply。传入的是该 Fiber 的子上下文。
↓
7
注册成为 Effect，状态变 ACTIVE执行期间通过 ctx 建立的注册全部记在 Fiber 名下；提供者上线后，等待它的消费者被唤醒。
↓
8
卸载：UNLOADING → DISPOSED逆序执行清理，释放服务，通知依赖者重新评估；父 Fiber 会连同子树一起卸载，并等待子树完成。

状态机可以单独画出来：

PENDING等依赖
→
LOADING执行 apply
→
ACTIVE已就绪
→
UNLOADING跑清理
→
DISPOSED已释放

LOADING 失败 → FAILED；ACTIVE 时依赖消失或更新配置 → UNLOADING → 重新 LOADING 或 DISPOSED。

用代码观察状态

官方教程里有一个很实用的诊断片段。它遍历注册表，把所有仍在等待依赖的插件打印出来：

diagnose.tsts
import { FiberState, type Context } from '@deepseek-ai/cordis'

export function apply(ctx: Context) {
  setTimeout(() => {
    for (const runtime of ctx.registry.values()) {
      for (const fiber of runtime.fibers) {
        if (fiber.state === FiberState.PENDING) {
          console.log(`${fiber.name} is PENDING — a required service is missing`)
        }
      }
    }
  }, 500)
}

这段代码背后的信息是：注册表是可枚举的。你可以随时知道应用里有哪些插件、它们处于什么状态、 谁在等谁。第 5 章会把这种诊断扩展成一张完整的“插件树体检表”。

包地图：核心、官方插件、Harness 插件

Cordis 的代码被拆成多个包。初学者最容易混淆的是：哪些是框架，哪些只是框架的插件，哪些又是 Harness 的业务。 下面这张表按“离核心的距离”排列：

包角色是否必需一句话
@deepseek-ai/cordis 核心 是 Context、Registry、Fiber、Service、Events、Logger。
@deepseek-ai/cordis-plugin-loader 官方插件 否 维护 Entry 树，按配置导入并挂载插件。
@deepseek-ai/cordis-plugin-include 官方插件 否 从 YAML / JSON 文件读取条目，支持 !!js 表达式。
@deepseek-ai/cordis-plugin-group 官方插件 否 把一组条目当作一个单元加载和卸载。
@deepseek-ai/cordis-plugin-hmr 官方插件 否 监听文件变化，卸载并重新加载对应插件。
@deepseek-ai/cordis-plugin-timer 官方插件 否 与卸载绑定的定时器、节流、防抖工具。
@deepseek-ai/cordis-plugin-logger-console 官方插件 否 把 logger 的消息输出到控制台。
@deepseek-ai/schemastery 配套库 否 配置 schema 与默认值；Cordis 接受任意 Standard Schema。
@deepseek-ai/dsh-* Harness 插件 否 工具注册表、LLM 适配器、会话、沙箱、agent loop 等业务能力。

上游对应名称为 cordis、@cordisjs/plugin-*；本仓库 vendor 后统一改为 @deepseek-ai 作用域。

边界 · 不要把 Harness 当成 Cordis

ctx.tools、ctx.llm、ctx.sessions 都是 Harness 插件注册的服务， 不是 Cordis 内置的。Cordis 本身不知道“工具”是什么，也不知道“模型”是什么。它只提供容器、依赖、事件和生命周期。 看懂这条边界，你就不会在 Cordis 文档里找 ctx.tools 的定义了。

最小栈与完整栈

你不需要一次性引入所有包。按需求逐层加：

你想要需要的包典型代码
只要容器与生命周期 cordis new Context() + ctx.plugin()
配置文件驱动 + loader + include ctx.plugin(Loader) + loader.create({ name: include, config })
分组与嵌套配置 + group 条目里写 group: true
开发时热更新 + hmr + timer + logger-console 条目里挂一个 HMR 插件，配置监听目录
完整 Harness 运行时 + 大量 dsh-* 插件 dsh 的 profile 配置

本章小结

  • Cordis 分三层：组合（main / yml）、加载（Loader）、运行（Context / Fiber）。只有运行层是必需的。
  • 六个核心部件：Registry、Fiber、Reflect、Events、Service、Logger。
  • 插件构成一棵树；父 Fiber 卸载会带走整棵子树，并等待子树清理完成。
  • 一次加载的关键节点：创建 Fiber → 检查 inject → 校验配置 → 执行插件 → ACTIVE；缺依赖就停在 PENDING。
  • Cordis 核心、官方插件、Harness 业务插件是三件不同的事，不要混为一谈。

自测一下

如果不用 Loader，Cordis 还能工作吗？

能。Loader 只是“从文件读配置并导入模块”的外围工具。你完全可以在 main.ts 里手动 ctx.plugin(A)、ctx.plugin(B)。代价是装配关系写死在代码里，失去配置驱动和热更新。

一个插件停在 PENDING，最可能的原因是什么？应该先查什么？

最可能是它的 inject 里某个服务没有提供者，或者提供者自己也停在 PENDING。 先列出该插件的 inject 列表，再逐个检查对应的 provide / Service 是否存在； 注意拼写和隔离作用域。

ctx.tools 是 Cordis 的核心服务吗？

不是。它是 DeepSeek Harness 的 @deepseek-ai/dsh-tools 插件注册的服务。 Cordis 只提供 ctx 这个容器；容器里放什么，由挂载的插件决定。
