插件与 Fiber

插件是 Cordis 的功能单元，Fiber 是这个单元“这一次运行”的生命周期。理解了两者的分工， 你就能回答初学者最常问的三个问题：插件为什么没启动？它什么时候被卸载？我注册的东西为什么不消失？

难度 入门 阅读 约 25 分钟 前置 第 4 章 关键词 状态机 · PENDING · dispose
本章你将学会
  • 写出函数、对象、类三种插件，并知道何时用哪一种；
  • 读懂 Fiber 的六个状态，尤其是 PENDING 与 FAILED；
  • 用 await ctx.plugin() 与 fiber.dispose() 精确控制生命周期；
  • 诊断“插件没有输出”的四步方法。

三种插件形态

Cordis 不要求插件继承某个基类，也不要求实现固定接口。它接受三种东西，并在内部统一成一个可执行回调：

shapes.tsts
import { Context } from '@deepseek-ai/cordis'

// 1. 函数插件：最轻量，直接调用
const fnPlugin = (ctx: Context) => {
  console.log('function plugin')
}

// 2. 对象插件：可以携带 name / inject / Config 等元数据
const objectPlugin = {
  name: 'object-plugin',
  apply(ctx: Context) {
    console.log('object plugin')
  },
}

// 3. 类插件：被 new 出来，适合需要实例状态的场景
class ClassPlugin {
  constructor(public ctx: Context) {
    console.log('class plugin')
  }
}

const root = new Context()
await root.plugin(fnPlugin)
await root.plugin(objectPlugin)
await root.plugin(ClassPlugin)
终端output
function plugin
object plugin
class plugin
形态怎么被调用适合注意
函数 plugin(ctx, config) 一次性装配、简单扩展、示例。 不能直接用 this；用 Object.assign 附加 inject 等元数据。
对象 plugin.apply(ctx, config) 需要可读的元数据、可复用的插件常量。 必须有 apply 方法，否则会被判为非法插件。
类 new plugin(ctx, config) 有实例状态、需要继承、要注册服务。 通常继承 Service，见第 6 章。

通过 Loader 从文件加载时，模块通常导出一个 apply 函数和一些元数据，Loader 会把整个模块命名空间 当成“对象插件”来处理。所以你在第 1 章看到的写法，和这里的函数插件是兼容的，只是入口不同。

插件可以携带哪些元数据

无论哪种形态，Cordis 都认识下面这些字段：

字段作用默认
name显示名，用于日志、诊断和 Fiber 名称。函数名或 'root'
inject声明依赖的服务名数组，或“服务名 → 配置”的对象。无依赖
Config配置 schema；启动前校验，失败则 FAILED。不校验
provide声明这个插件会提供的服务名（Loader 用来做静态分析）。由运行时决定
intercept声明需要读取哪些服务的 intercept 配置。无

inject 有两种写法。数组形式最常见；对象形式可以为某个服务附带配置（intercept）， 只有当服务作者支持时才有意义：

inject-forms.tsts
export const inject = ['db', 'logger']

// 或者：为 logger 附带局部配置
export const inject = {
  db: null,
  logger: { level: 3 },
}

ctx.plugin 到底返回什么

每调用一次 ctx.plugin()，Cordis 就创建一个 Fiber。它既是运行实例的句柄， 也是一个“可等待对象”：你可以 await 它，等当前加载流程稳定，或捕获启动错误。

fiber.tsts
import { Context } from '@deepseek-ai/cordis'

const root = new Context()

const fiber = root.plugin(function demo(ctx) {
  console.log('apply 开始')
  ctx.effect(() => () => console.log('清理'))
  console.log('apply 结束')
})

console.log('uid:', fiber.uid)
await fiber
console.log('state:', fiber.state)
await fiber.dispose()
console.log('disposed uid:', fiber.uid)
终端output
uid: 1
apply 开始
apply 结束
state: 2
清理
disposed uid: null

state: 2 是 FiberState.ACTIVE 的数值。实际代码里不要硬编码数字，用 fiber.state === FiberState.ACTIVE 比较。要注意的是，ctx.plugin() 返回的 Fiber 是一个被包装过的对象：它带有 then 方法，所以既能当句柄用，也能直接 await。

为什么 uid 会变 null

uid 是 Fiber 在注册表里的唯一编号，根 Fiber 固定为 0。一旦开始卸载，Cordis 会把 uid 清空，表示“这个实例已经不属于任何注册表”。如果你在异步回调里看到 uid === null， 说明插件已经被卸载了，不应该再访问它的服务。

await 不等于“依赖已就绪”

await ctx.plugin() 等待的是“当前加载流程稳定”，而不是“插件一定 ACTIVE”。 如果依赖缺失，Fiber 会合法地停在 PENDING，此时没有正在进行的初始化，await 会立刻返回。 要确认就绪，请检查 fiber.state === FiberState.ACTIVE；要等依赖出现，请挂载提供者或监听状态变化。

六个状态，一张图

PENDING等依赖
→
LOADING执行 apply
→
ACTIVE已就绪
→
UNLOADING跑清理
→
DISPOSED已释放

LOADING 抛错 → FAILED；ACTIVE 时依赖消失或配置更新 → UNLOADING → 重新 LOADING。

状态含义此时能做什么常见原因
PENDING 已创建，但依赖未齐，插件代码尚未执行。 等待；补上提供者。 inject 中的服务没人提供，或提供者也在 PENDING。
LOADING 正在校验配置、执行插件函数。 等待 await fiber。 正常的启动过程；异步初始化会停留更久。
ACTIVE 插件已加载，服务已上线。 正常使用。 —
FAILED 配置校验或插件函数抛错。 修复后更新配置或重新挂载。 schema 不匹配、apply 内异常。
UNLOADING 正在逆序执行清理。 等待 dispose() 完成。 主动卸载、依赖消失、热更新。
DISPOSED 已释放，不能再次启动。 重新 plugin 一个新实例。 —

PENDING：最常见的“没有输出”

初学者最容易慌的时刻：插件写好了，也挂载了，控制台却什么都没有。先别改代码， 看看它是不是在等依赖。下面这个例子故意缺一个 db：

pending.tsts
import { Context, FiberState } from '@deepseek-ai/cordis'

const root = new Context()

const fiber = root.plugin({
  name: 'needs-db',
  inject: ['db'],
  apply() {
    console.log('loaded!')
  },
})

console.log('is pending:', fiber.state === FiberState.PENDING)

// 补上提供者，Fiber 才会开始加载
root.provide('db', {})

await fiber
console.log('is active:', fiber.state === FiberState.ACTIVE)
终端output
is pending: true
loaded!
is active: true

PENDING 不是错误，而是一种合法的等待状态。Cordis 不知道提供者会不会在五秒后、五分钟后来， 所以它选择等，而不是崩溃。这个设计让“先加载消费者、后加载提供者”成为可能，也让配置文件里的顺序变得无关紧要。

PENDING 的副作用

处于 PENDING 的 Fiber 不会让 Node 的事件循环保持活跃。如果整个应用只有它一个“待办”，进程会安静地以状态码 0 退出， 看起来像“什么都没发生”。这不是 bug，而是“没有提供者，也没有其他工作”时的诚实结果。

诊断 PENDING 的四步

  1. 列出所有 Fiber 的状态，找到 PENDING 的那个；
  2. 看它的 inject 列表，逐个确认有没有 provide / Service 注册同名服务；
  3. 检查提供者自己是不是也在 PENDING，或因为配置错误停在 FAILED；
  4. 如果用了 isolate，确认提供者和消费者在同一个隔离作用域里。
diagnose.tsts
import { FiberState, type Context } from '@deepseek-ai/cordis'

const STATE = ['PENDING', 'LOADING', 'ACTIVE', 'FAILED', 'DISPOSED', 'UNLOADING']

export function apply(ctx: Context) {
  setTimeout(() => {
    for (const runtime of ctx.registry.values()) {
      for (const fiber of runtime.fibers) {
        console.log(`${fiber.name}: ${STATE[fiber.state]}`)
      }
    }
  }, 500)
}

这里的 STATE 数组顺序对应 FiberState 的枚举顺序。生产代码更推荐直接比较枚举成员， 或调用 FiberState[fiber.state]。

依赖不是一次性的

inject 不是“启动时检查一次”的静态声明。只要运行中提供者消失，依赖它的插件就会被卸载； 提供者回来，它又会重新加载。这保证了消费者永远不会持有一个已经失效的服务引用。

reload.tsts
import { Context } from '@deepseek-ai/cordis'

const root = new Context()

const provider = await root.plugin(function dbProvider(ctx) {
  ctx.provide('db', { query: () => 'ok' })
  ctx.effect(() => () => console.log('provider: down'))
})

const consumer = await root.plugin(Object.assign((ctx) => {
  console.log('consumer: up')
  ctx.effect(() => () => console.log('consumer: down'))
}, { inject: ['db'] }))

await provider.dispose()
console.log('--- provider disposed ---')
终端output
consumer: up
provider: down
consumer: down
--- provider disposed ---

提供者卸载会触发消费者卸载：provider.dispose() 返回时，消费者也已经清理完毕。 但两个清理日志的先后不是契约——它取决于 Effect 的注册顺序。这里提供者的清理函数注册得更晚， 所以先执行；真正保证的是“消费者不会继续持有一个已经下线的服务”。

如果你不想让插件随提供者消失，可以改用可选依赖：

optional.tsts
const plugin = (ctx: Context) => {
  const db = ctx.get('db')
  if (!db) {
    console.log('no db, running in degraded mode')
    return
  }
  console.log('db is ready')
}

可选依赖不会被 Fiber 跟踪，所以提供者消失时插件不会自动卸载。这是优点也是风险： 你必须在每次使用前重新判断，不能把 db 缓存到模块级变量里。

子插件与卸载完成

在插件的 apply 里再次调用 ctx.plugin()，新插件会成为当前 Fiber 的子节点。 父节点卸载时，子节点会作为父节点的一个 Effect 被卸载；父节点会等待子节点的异步清理完成。

children.tsts
const parent = root.plugin(function parentPlugin(ctx) {
  ctx.plugin(function childPlugin(ctx) {
    ctx.effect(() => () => console.log('child down'))
  })
  ctx.effect(() => () => console.log('parent down'))
})

await parent
await parent.dispose()
终端output
parent down
child down

这里父清理先执行，是因为它比“子插件”更晚注册；Effect 按注册逆序撤销。 顺序本身不是契约：真正保证的是 parent.dispose() 返回时，子插件也已经清理完毕。 如果你需要“先关子、再关父”的严格顺序，把它们放进同一个 disposer 里显式 await， 而不是依赖注册顺序。

Fiber 上常用的成员

成员类型用途
fiber.ctxContext这个插件运行所在的子上下文。
fiber.stateFiberState当前状态；诊断时最有用。
fiber.namestring沿父链找到的显示名，根为 'root'。
fiber.uidnumber | null注册表编号；卸载后为 null。
fiber.dispose()() => Promise<void>卸载插件及其子插件，等待清理完成。
await fiberPromiseLike<Fiber>等待启动稳定；启动错误会在这里抛出。
fiber.update(config)(config) => void校验新配置并重启插件；HMR 用它。
fiber.restart()() => Promise<void>用当前配置卸载再加载。
什么时候需要保存 Fiber

大多数插件不需要保存自己的 Fiber——Cordis 会在父节点卸载时处理。需要保存的典型场景是： 你想在运行中主动卸载某个子插件（例如“关闭某个功能”），或者测试里需要精确控制启动/停止。

插件出错时会发生什么

  • 插件形态非法：ctx.plugin(42) 会同步抛错，提示需要函数或带 apply 的对象。
  • 配置校验失败：Fiber 进入 FAILED，await fiber 会抛出 ValidationError，错误信息指出字段路径。
  • apply 抛错：Cordis 记录错误，Fiber 进入 FAILED；await fiber 会把原错误抛给调用方。
  • 清理函数抛错：错误会被 logger 记录，不会阻止其他清理继续执行；但资源可能处于不一致状态。
  • 参数插件已卸载：在已卸载的父上下文里再调用 ctx.plugin，会抛出 INACTIVE_EFFECT。

一个容易忽略的细节：Cordis 默认用 logger 记录启动错误，而 logger 默认只把消息放进内存缓冲区。 如果你没有挂载控制台导出器，错误可能“看不见”。调试时加上 @deepseek-ai/cordis-plugin-logger-console，或者自己注册一个 exporter。

本章小结

  • 插件有三种形态：函数、{ apply } 对象、类；Cordis 在内部统一成回调。
  • name、inject、Config、provide 是插件最重要的元数据。
  • 每次 ctx.plugin() 产生一个 Fiber；它可等待、可卸载、可更新。
  • PENDING 是等依赖，FAILED 是出错；两者的排查方向完全不同。
  • 依赖会持续跟踪：提供者消失，消费者卸载；提供者回来，消费者重载。
  • 父插件卸载会一并卸载子插件，并等待子插件的异步清理完成；具体先后遵循 Effect 的逆序规则。

自测一下

函数插件和对象插件，除了写法之外最重要的区别是什么？

对象插件可以自然地携带 name、inject、Config 等元数据； 函数插件也能通过 Object.assign 附加这些字段，但可读性差一些。运行时的调用方式也略有不同： 函数被直接调用，对象调用其 apply。

插件停在 PENDING，你会按什么顺序排查？

先枚举 Fiber 状态确认是 PENDING；再读该插件的 inject 列表；然后逐个查找同名服务的提供者， 确认提供者不是 FAILED/PENDING；最后检查 isolate 作用域是否一致。

为什么“先加载消费者、后加载提供者”也能工作？

消费者会停在 PENDING，等提供者注册服务时，Cordis 通过 Reflect 通知所有依赖该服务的 Fiber， 重新计算依赖并唤醒它们。加载顺序由依赖关系决定，而不是配置文件或代码顺序。
